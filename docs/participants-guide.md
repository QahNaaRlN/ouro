# Участники standalone Ouro

В «Участники» оператор создаёт именованные человеческие идентичности. Отдельные браузеры входят по своим ключам, а решения, ожидания и публикации сохраняют серверный ID автора. Две обычные демо-вкладки продолжают быть одним локальным оператором.

## Вход и приглашение

1. На доверенном локальном рабочем месте откройте «Участники», укажите имя и нажмите «Создать участника».
2. Скопируйте ключ и передайте его нужному человеку. Он показывается один раз; после закрытия панели восстановить прежнее значение нельзя. При утрате отзовите запись и выдайте новый ключ.
3. Участник открывает тот же Ouro и вводит ключ в «Войти участником». Отдельная сессия заменяет идентичность только этого браузера. В истории отображается имя и неизменяемый ID из реестра.
4. Ключ можно использовать повторно до отзыва: после выхода, истечения сессии или перезапуска сервера потребуется войти снова. Ключ не сохраняется в localStorage/sessionStorage и не включается в предметную историю.

Все участники имеют человеческие полномочия **текущего проекта**: изменение ожиданий, решения и приёмку DoD. Ключи участников выдаёт и отзывает только доверенный оператор. Внешнее SSO, роли с разными правами и многоарендность этим реестром не предоставляются.

Учебный симулятор также остаётся инструментом доверенного локального оператора. Именованные участники работают с назначенными настоящими агентами; их ключ не делегирует полномочия симулятора.

## Что означает локальный оператор

`npm run dev/start` включает loopback demo. Любой браузер на этом доверенном локальном рабочем месте может открыть новую демо-сессию оператора. После выхода участника и удаления его cookie локальный браузер снова получает оператора при загрузке. Поэтому отзыв участника ограничивает его ключ и сессию; он не лишает владельца локальной машины доступа к самому приложению.

На внешнем hostname демо-сессия не выдаётся, даже если `OURO_LOCAL_DEMO=1`. Для удалённого HTTPS origin требуется явный `OURO_PUBLIC_URL`; участник входит по своему ключу. Это не заменяет отдельное решение о развёртывании и внешней identity.

## Отзыв и история

Оператор нажимает «Отозвать доступ» в реестре. Следующие запросы с этим ключом/cookie отклоняются, в том числе попытка повторить старую команду. Открытый SSE-поток повторно проверяет доступ перед дальнейшим чтением и выдачей снимка. Уже полученные браузером данные невозможно отозвать; факты авторства остаются в истории.

Недействительная, истёкшая или отозванная cookie участника **не переключается автоматически** на локального оператора. Войдите с действующим ключом либо явно выйдите из сессии. При явном Authorization сервер проверяет именно его; неверный bearer не заимствует права cookie.

Сессия имеет абсолютный срок12 часов. Cookie подписана, HttpOnly, SameSite=Strict, на HTTPS — Secure. Серверный signing key этой standalone версии находится в памяти: перезапуск требует повторного входа. Хранилище сохраняет только SHA-256 случайных256-bit ключей и append-only регистрации/отзывы; при каждом запросе проверяется действующий реестр, а запись повторяет проверку внутри транзакции.

## Изученные ориентиры

Фактически прочитаны разделы [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) о Session ID Entropy, Secure, HttpOnly, SameSite и Session Expiration; [исходный текст](https://raw.githubusercontent.com/OWASP/CheatSheetSeries/master/cheatsheets/Session_Management_Cheat_Sheet.md). Применены CSPRNG256-bit ключи, ограниченный срок cookie, явные атрибуты и серверная проверка отзыва. SameSite не считается самостоятельной заменой защиты записи: остаются JSON и Origin/Host проверки. Полное соответствие OWASP и внешний identity-provider не заявляются.
