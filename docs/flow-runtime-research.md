# Учёт проходов Flow: источники и решения

29.10.2026 · основание [OURO-ENG-000014](specs/flow-runtime.md). Здесь перечислены фактически прочитанные части первоисточников и границы их применения. Результаты выполнения тестов ведутся отдельно в [журнале SDD/TDD](plans/flow-runtime.md).

## W3C SCXML: событие, guard и выбор перехода

Прочитаны нормативные [§3.5 `<transition>`](https://www.w3.org/TR/scxml/#transition) и [§3.13 Selecting and Executing Transitions](https://www.w3.org/TR/scxml/#SelectingTransitions), а также вводная часть информативного [Appendix D](https://www.w3.org/TR/scxml/#AlgorithmforSCXMLInterpretation). §3.5 связывает переход с событием и guard. §3.13 определяет enabled transition, конфликты, приоритеты и microstep; Appendix D прямо назван иллюстративным алгоритмом, а не единственным способом реализации интерпретатора.

В Ouro применён принцип: явная команда/факт → проверка текущего состояния и разрешений → атомарная запись результата перехода. Завершение текущего прохода, traversal и открытие следующего ready-прохода фиксируются вместе. Перерисовка линии, получение heartbeat или выбор элемента холста не являются переходом.

Ouro не исполняет SCXML и не реализует его полный алгоритм выбора: нет иерархических state configurations, parallel regions, executable content, eventless macrosteps или вычисления `cond`. В узле condition нужно явно предъявить `edgeId` и evidence. Автоматическое «взять первый подходящий исход» не подменяет человека и не добавляется из сходства с SCXML.

## OMG BPMN 2.0.2: исключающий путь и синхронизация

Прочитан официальный [PDF BPMN 2.0.2](https://www.omg.org/spec/BPMN/2.0.2/PDF), конкретно §10.6.2 Exclusive Gateway (печатная стр. 289), §10.6.4 Parallel Gateway (стр. 292–293), §13.4.1 Parallel Gateway и §13.4.2 Exclusive Gateway (стр. 434–435). Это чтение указанных разделов, а не заявление об изучении всего стандарта.

| Прочитанное правило | Решение в Ouro | Граница |
|---|---|---|
| Exclusive Gateway выбирает ровно один исход при активации | В enforced-профиле один текущий проход и один реально выбранный преемник | В Fork выбирает человек; condition требует явного edgeId/evidence, выражения BPMN не вычисляются |
| Exclusive Merge пропускает поступивший путь | Несколько входящих рёбер допустимы; каждый фактический вход создаёт новый run | Приход одного пути не означает выполнение остальных |
| Parallel Gateway раздаёт токены всем исходам и ждёт входы при синхронизации | Параллельный fork/join в этот профиль не входит | Несколько стрелок не трактуются как AND-join; нельзя объявить слияние ожиданием всех предшественников |

Понятие отдельного посещения важно для повторной проверки: один `nodeId` может иметь несколько `runId` и последовательные `visit`. Старый успешный проход не становится текущим, и его решение Fork не разрешает новый проход. Не выбранный исход не создаёт выдуманный skipped-run.

Данный профиль не является BPMN engine и не заявляет переносимость BPMN XML или соответствие operational semantics всего стандарта. Внешние агенты и наблюдаемые system-шаги не запускаются самим холстом.

## React Flow и доступность

Прочитана [React Flow Accessibility](https://reactflow.dev/learn/advanced-use/accessibility): Tab-переход по focusable nodes/edges, Enter/Space для выбора, стрелки для перемещения, auto-pan на фокус и настройка `ariaLabelConfig`. Выбор узла/ребра нужен для инспекции; бизнес-команды остаются отдельными видимыми действиями. Нельзя использовать нажатие линии как неявное разрешение перехода.

Дополнительно прочитаны [WCAG 2.2 §2.1.1 Keyboard](https://www.w3.org/TR/WCAG22/#keyboard) и [§1.4.1 Use of Color](https://www.w3.org/TR/WCAG22/#use-of-color): функция доступна с клавиатуры, цвет не является единственным способом передачи смысла. Поэтому статус подписывается текстом, а таблица и инспектор предоставляют доступ к тем же данным без точного попадания мышью в ребро. Полная WCAG-приёмка всего приложения этим чтением не заявляется.

## Почему run отделён от шага и исполнения

FlowDefinition — неизменяемое ожидание ревизии. Execution — разрешённая попытка работы. Run — одно посещение узла в этой попытке. Traversal — зафиксированный переход между двумя конкретными runs. Action — отдельный отчёт о факте, который может ссылаться на run, но не передвигает процесс автоматически.

Такое разделение сохраняет проверяемую историю при цикле, позднем отчёте, повторе запроса и человеческом исправлении решения. Это продолжает принятую [методологию неизменяемых событий](status-methodology.md), а не заменяет её mutable status-полем на карточке.

Внеплановое ожидание сохраняется как запрос текущего run с серверным flowInterrupt. Оно не дорисовывает задним числом Question/Fork/Blocker в immutable схему, а его операционное решение не подменяет traversal. Неуспех текущего прохода основной незавершённой попытки активной ревизии отражается в Spec.blocked до разрешённого retry; это сигнал необходимого человеческого действия, а не утверждение о физической остановке внешнего процесса.

## Осознанные ограничения

- Новый режим включается явно только при новом человеческом назначении; legacy execution и старые Action не дополняются предполагаемыми проходами.
- Один текущий проход, до 1000 проходов на execution; нет автоматического scheduler, таймеров, параллельных ветвей и исполняемых выражений.
- `result` завершает процессный маршрут. Успех execution, подтверждение физической остановки и human acceptance DoD — отдельные факты.
- JSON Schema описывает DTO; выбор, permissions, ссылки на реальный run и состояние исполнения проверяет сервер. Прохождение структурной валидации не даёт полномочий.
- Самостоятельный `@ouro/protocol` описывает эти данные и помогает их проверять, но не становится хостом выполнения. [Установка библиотеки](../packages/protocol/README.md), [пользовательская инструкция](flow-runtime-guide.md).
