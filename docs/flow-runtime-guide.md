# Проходы процессной схемы · alpha.13

[SDD](specs/flow-runtime.md) · [Результаты и границы проверок](plans/flow-runtime.md) · [Прочитанные ориентиры](flow-runtime-research.md).

Обычная схема описывает возможные шаги. **Строгий учёт проходов** добавляет подтверждённое состояние каждого реального посещения шага и историю переходов. Это отдельная ось: состояние шага не заменяет состояние execution или приёмку спеки.

## Включить режим

1. Создайте схему во вкладке **«Процесс»**, проверьте шаги и исходы, предложите новую ревизию и отдельно активируйте её.
2. При создании **новой** попытки выберите назначенного агента и включите **«Строгий учёт проходов»**. В API это человеческая команда `startExecution` с `flowTracking:'enforced'`.
3. Сервер проверит поддерживаемый профиль. Вместе с разрешением попытки появляется единственный ready-проход начального узла. Пока агент не подтвердил `ouro.confirm_started`, начинать проход нельзя.
4. После ACK агент читает `ouro.get_context`: `work[].execution.flowRuntime` содержит runs/traversals и currentRunId, а `work[].flowProgress` — доступность текущих действий и переходов с причинами запрета.

Без флажка сохраняется прежнее поведение. Режим нельзя дописать задним числом в старую попытку: старые Action не превращаются в предполагаемые проходы. Существующие ревизии и их hashes не меняются.

Для первого знакомства удобна новая учебная спека со схемой action → result. Если у спеки уже есть незавершённая legacy-попытка, новый флажок не переключает её режим: завершите или корректно остановите прежнюю работу по действующей методологии, затем разрешайте новую попытку.

Для строгого назначения клиент должен поддерживать `ouro.report_flow_step` и контракт 0.1.1: проверьте tools/list и ресурс `ouro://protocol/manifest`. Старому агенту оставляйте legacy-режим до обновления клиента. Уже разрешённая enforced-попытка не ослабляется автоматически, если агент не передал runId.

## Поддерживаемая схема

В попытке один текущий проход, все исходы исключающие:

| Узел | Исходы и способ продолжения |
|---|---|
| action, wait, question, blocker | Ровно один исход |
| condition | При complete явно задаются edgeId и evidence; выражение из подписи не вычисляется |
| fork | До 10 исходов, у каждого уникальный optionId; вариант должен присутствовать в человеческом запросе |
| result | Исходящих связей нет; завершение фиксируется отдельной командой прохода |

Несколько входящих рёбер — обычное слияние выбранного пути. Система не ждёт все входы как AND-join. Для Blocker нужен owner=agent; Question/Fork остаются human-owned по базовым правилам схемы. Параллельные fork/join, таймеры и автоматическое выполнение кода не поддерживаются. Схема другого профиля остаётся доступной для чтения и редактирования; её строгий запуск отклоняется с объяснением. На одну execution разрешено не более 1000 проходов.

## Идентификаторы

| Поле | Что обозначает |
|---|---|
| executionId | Разрешённую попытку по точной immutable ревизии |
| flowNodeId | Узел плана в этой ревизии |
| runId | Одно посещение узла; передаётся в `ouro.report_flow_step` |
| visit | Порядковый номер посещения данного nodeId внутри execution |
| flowStepRunId | Привязку Action/Question/Fork/Blocker к конкретному проходу |
| requestId | Одну бизнес-команду; повтор сохраняет ID и всё тело |
| actionId | Одно действие через фазы started/completed/failed; не равно runId |

При возврате по циклу узел получает новый runId и следующий visit. Старые evidence, результат и traversal сохраняются. Чужая execution или другая ревизия не меняют выбранный проход.

## Сообщить состояние прохода через MCP

Назначенный агент вызывает `ouro.report_flow_step`. Пример формы старта; замените ID и версию значениями из своего свежего контекста:

```json
{
  "executionId": "ID назначенной попытки",
  "runId": "currentRunId из её flowRuntime",
  "phase": "start",
  "requestId": "стабильный ID этой команды",
  "expectedVersion": 123
}
```

| Фаза | Допустимое исходное состояние | Результат |
|---|---|---|
| start | Текущий ready | running; для wait — waiting |
| complete | Текущий начатый проход, все применимые guards выполнены | succeeded, реальный traversal и следующий ready; на result завершается процесс |
| fail | Текущий начатый проход | failed с evidence; продолжение требует отдельного решения о повторе |

Для complete/fail обязательно evidence. Человеческое подтверждение start human/system-шагов тоже требует evidence. EdgeId выбирается только при complete: если нужен выбор исхода, передайте его точный ID. Start/fail не выбирают ребро. Старт, завершение и неуспех — разные команды с разными requestId. При сетевом повторе одной команды сохраните прежние phase/runId/edgeId/evidence/requestId/expectedVersion: сервер сначала ищет квитанцию и не создаёт второй traversal. При конфликте версии прочитайте контекст; не подменяйте expectedVersion автоматически.

Start, complete, retry и skip требуют running execution, действующей ревизии и общих разрешающих guards. Fail фиксирует уже случившийся неуспех текущего начатого running/waiting-прохода: при незавершённой execution его можно сообщить и после паузы, stop request или смены ревизии. Он требует правильного автора/назначения и evidence, не открывает новый узел, не возобновляет execution и не очищает stop-флаги. Failed-run сохраняется текущим для разбора; retry остаётся отдельной человеческой командой со строгими guards.

`ouro.report_action` остаётся отдельным отчётом о работе. Его phase completed не завершает проход. В строгой попытке новые отчёты указывают flowStepRunId. Для совпадающего с типом узла планового отчёта flowNodeId сервер выводит из run; переданный ID обязан совпасть. Внеплановые вопросы описаны ниже. Поздняя фаза уже существующего actionId остаётся на его исходном run и не двигает новый проход: нельзя заменить исходный flowStepRunId новым currentRunId.

## Исполнитель и человеческие решения

Агент подтверждает agent-owned шаги. Для human/system action, wait, condition и result факты подтверждает человек с evidence. System означает наблюдаемый системный шаг, а не наличие встроенного runner.

Для Question/Fork агент может начать шаг и создать связанный запрос человеку. В строгом режиме запрос связывается с текущим run; у Question сервер нормализует даже `blockingScope:'none'` до блокировки execution. Для каждого нового прохода нужны его актуальные человеческие факты:

- Question — ответ человека с исходом `answer` и подтверждение применения; `reject` не разрешает продолжение.
- Fork — выбранный optionId и подтверждение применения. У переданного edgeId поле `edge.optionId` должно совпадать с `chosenOptionId` решения; сами edgeId и optionId — разные идентификаторы.
- Blocker — согласованный путь устранения и отдельное подтверждённое устранение с evidence по прежнему [remediation-сценарию](methodology-guide.md). Завершение прохода не заменяет `ouro.clear_blocker`.

Ответ человека сам не передвигает процесс. Применение решения, отдельное разрешение продолжения и ACK агента сохраняются разными фактами; только после них допустимо complete. Старый applied Fork не разрешает повторное посещение того же узла. Отзыв/отклонение запроса не считаются разрешением, а одобрение плана Blocker не является его устранением.

### Внеплановый вопрос, выбор или блокер

Question/Fork/Blocker можно обнаружить во время любого уже начатого текущего run. Например, во время action потребовался новый вопрос человеку. Передайте flowStepRunId текущего прохода и **не указывайте flowNodeId**, если тип запроса не совпадает с типом узла. Сервер сохранит связь с проходом и свой признак `flowInterrupt:true`, не приписывая вопрос узлу другого типа. Явно неверный flowNodeId отклоняется; признак flowInterrupt агент сам не передаёт.

До complete нужны положительные применённые решения всех актуальных внеплановых Question/Fork либо одобренное и подтверждённое устранение внепланового Blocker; затем отдельно требуются разрешение продолжения и ACK. Применяются текущие линии исправления/замещения запросов этого run. Исключение — утративший актуальность и отозванный interrupt-Question/Fork: обычный шаг можно продолжить после отдельного человеческого разрешения и ACK, без фиктивного fail/retry. Плановый Question/Fork всё равно требует положительного запроса этого прохода, а отзыв Blocker не устраняет препятствие. Операционный выбор interrupt-Fork не выбирает ребро диаграммы: плановый Fork и condition сохраняют собственные правила выбора исхода.

Wait после start остаётся waiting до явного complete с evidence. Истечение времени, heartbeat и отсутствие ответа ничего не завершают. StopRequested не является доказательством фактической остановки.

## Повтор и пропуск

Человек может вызвать `retryFlowStep` для failed-прохода с причиной. Создаётся новый ready-run того же узла с retryOfRunId; прежний failed не переписывается.

Если runtime основной незавершённой попытки активной ревизии находится в failed, спека показывается blocked до допустимого человеческого retry. Это отдельная причина блокировки; retry не обходит оставшиеся человеческие запросы, stop-флаги или физические препятствия. Failed execution — уже завершённая попытка, её шаг нельзя возобновить командой retry того же исполнения.

Человеческий `skipFlowStep` требует причины и evidence. Он допустим только для текущего ready action/wait с одним исходом и при выполненных общих guards. Нельзя пропустить Question/Fork/Blocker, переписать terminal run или обойти физический блокер. Не выбранные альтернативы не получают выдуманный skipped: эти узлы могут быть посещены позже.

## Читать граф, таблицу и историю

Во вкладке **«Процесс»** выберите нужную execution. В блоке **«Учёт проходов процесса»** нажмите **«Открыть текущий шаг»**. В инспекторе **«Проходы узла»** поле **«Проход узла»** позволяет выбрать конкретное посещение. Карточка узла показывает последний зарегистрированный проход; непосещённый узел — **«Нет зарегистрированных проходов»**. После повторного посещения прежний runId остаётся доступным для разбора. Live-обновление не подменяет явно выбранный старый проход текущим. Чтобы продолжить после перехода, снова откройте текущий шаг: выбор исторического run не делает его текущим.

В разделе **«Доступность перехода»** подпись **«Доступен»** (`available`) означает допустимость, **«Недоступен»** (`blocked`) сопровождается причиной, **«Переход зафиксирован»** (`taken`) — реальный traversal выбранного прохода, **«Не выбран в этом проходе»** (`not_selected`) — другой исход этого прохода. **«Возможный путь»** (`possible`) относится к плану без строгого прохождения или к другому узлу выбранной схемы: это не подтверждённый переход. При отправке команды сервер повторно проверяет состояние и права. Решение Fork «выбрано» и факт traversal различаются. Клик по ребру только открывает сведения. Отображение черновика или другой исторической ревизии не наследует статусы текущей попытки. Таблица предоставляет те же данные без выбора тонкой линии мышью.

Для своего или наблюдаемого системного шага выберите **«Действие человека»**, заполните **«Основание действия»**; для retry/skip укажите **«Причину действия»**, а при выборе исхода — **«Переход после шага»**. Нажмите **«Записать действие человека»**. Недоступные действия сопровождаются объяснением, например отсутствием ACK или незавершённым запросом человеку.

Если результат отправки не подтверждён, форма сохраняет исходные автора, runId, requestId, тело и версию. Откройте **«Проверить отправленное действие»** в сводке и используйте **«Повторить то же действие»** для получения квитанции; новые ID и основание команды не подставляются. Неподтверждённая отправка блокирует новую команду этой execution. После явного отказа до записи, например VERSION_CONFLICT, изучите события и нажмите **«Проверил события перед действием»**, затем подготовьте новую команду. Сетевой сбой или потеря авторизации сами по себе не доказывают отсутствие записи.

Завершённый result не принимает DoD и не отправляет `complete_execution` автоматически. Агент отдельно сообщает итог execution; succeeded в строгом режиме допускается только после result. Человек отдельно проверяет каждый обязательный критерий и принимает спеку. Отмена или неуспех execution закрывают авторизацию открытого прохода и не доказывают физической остановки внешнего процесса.

## Учебная проверка с симулятором

В попытке, назначенной **«Симулятору агента»**, в поле **«Действие человека»** есть отдельные варианты **«Учебный симулятор: Начать шаг»**, **«Учебный симулятор: Завершить шаг»** и **«Учебный симулятор: Сообщить ошибку»** для выбранного run. Сервер проверяет назначение и владельца шага теми же guards. Эти действия добавляют явно синтетические evidence вида `simulation://ouro/flow/...`; они не являются работой внешнего агента или доказательством реальной проверки файлов. Для чужой зарегистрированной агентской попытки симулятор не подставляет отчёты.

Для реального агента используйте MCP-сценарий выше. Human/system шаги подтверждает человек; наличие кнопки или симулятора не меняет owner immutable узла.

## Контракт вне Ouro

Runtime DTO, новый инструмент и run linkage описаны в `@ouro/protocol@0.1.1`. [Самостоятельная установка, ESM/CommonJS, TypeScript и CLI](../packages/protocol/README.md) и [общая инструкция протокола](protocol-guide.md) остаются отдельными от запуска приложения. Библиотека проверяет формат и переносимые правила; она не создаёт назначения, не выполняет код и не выдаёт человеческие полномочия. Версия 0.1.0 не переписывается; старые агенты и попытки продолжают использовать legacy-режим в его границах.
