# Литература и решения, применённые в прототипе Ouro

Дополнение alpha.4: перечитаны [WHATWG SSE§9.2](https://html.spec.whatwg.org/multipage/server-sent-events.html), [MDN SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events), [ReadableStream](https://developer.mozilla.org/en-US/docs/Web/API/Streams_API/Using_readable_streams) и установленная Next Streaming документация. Полный snapshot с cursor выбран для синхронного безопасного принятия; Last-Event-ID native меняется до callback, поэтому испорченный frame требует нового соединения от appliedcursor. Применены demand-driven pull/backpressure/cancel, heartbeat без продвижения ID и короткая подписка для re-auth. Измерение transport-open не подменяет подтверждение истории; canonical immutable prefix и core replay защищают согласованность представления. Архитектура остаётся одним SQL-агрегатом, не объявленным промышленным брокером.

Дополнение alpha.3 (29.10.2026): перед реализацией Flow повторно прочитаны [React Flow Accessibility](https://reactflow.dev/learn/advanced-use/accessibility), [Layouting](https://reactflow.dev/learn/layouting/layouting) и используемые положения [SCXML](https://www.w3.org/TR/scxml/). Применены доступные формы вместо обязательного drag, русские ARIA-инструкции, геометрия отдельно от предметных связей и отсутствие fit-view при приходе фактов. Flow допускает циклы с выходом; Roadmap остаётся DAG. Явная ссылка факта не превращает новое название узла в доказательство: подсветка исполнения отсутствует у редактируемого draft. Граф автомата показывает разрешение/ACK раздельно и выводит случившиеся переходы через тот же replay, что и приложение. Это собственная нотация Ouro, не BPMN/SCXML-интерпретатор.

Дополнение `0.1.0-alpha.2`: при разработке agent-connect изучены [MCP transports 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports), [официальный SDK server guide](https://github.com/modelcontextprotocol/typescript-sdk/blob/v1.x/docs/server.md), [authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization), [Claude Code](https://code.claude.com/docs/en/mcp) и [Cursor](https://cursor.com/docs/mcp). Проверены фактические API npm `@modelcontextprotocol/sdk@1.32.2`. Выбраны stateless Streamable HTTP с новым server/transport на запрос и stdio bridge к тому же backend; это сохраняет единственного владельца PGlite и позволяет подключать разные MCP-клиенты. Применены publishable runtime tool schemas, отдельный агентский bearer и явные ACK. OAuth authorization-server/discovery, прямой запуск LLM и постоянная UI SSE-подписка в пакет не включены. Совместимость подтверждается независимыми официальными SDK Clients обоих transport, не заявлением о полном испытании всех IDE.

Дата исследования: 2026-10-28. Документ дополняет [ТЗ](TZ-Ouro-OS.md), [ТС](TS-Ouro-OS.md), [статусную методологию](status-methodology.md) и [правила диаграмм](diagram-methodology.md). Это обоснование выбранного подхода, а не заявление о реализации всего стандарта или сравнении всех доступных продуктов. Точный объём работающего прототипа и результаты проверок фиксируются отдельно в README и отчёте реализации.

## 1. Как выбирались ориентиры

Сначала проверяются предметные ограничения Ouro: решения принимает человек; история не переписывается; успех агента отличается от приёмки результата; карта зависимостей не должна превращаться в произвольный рисунок. Затем выбираются источники, объясняющие соответствующие механизмы. Приоритет — нормативные документы и документация самих разработчиков, а не подборки инструментов.

Для этого исследования действительно открыты и прочитаны соответствующие разделы страниц ниже, включая PDF BPMN. Исследование не охватывает все страницы объёмных стандартов. У каждой ссылки указано конкретное применение и граница заимствования. Слово «лучший» здесь означает наиболее подходящий известный подход для заданных ограничений; универсальное превосходство или проведённое измерительное сравнение не заявляется.

## 3. Принятые инженерные решения

### ADR-01. Три графа с разным смыслом

**Контекст.** В одном интерфейсе нужны план, возможный процесс и история. Если считать их одинаковыми схемами, повторная проверка может переписать прошлый узел, а нарисованная стрелка — ошибочно разрешить запуск.

**Решение.** Roadmap хранит спецификации и явные обязательные зависимости; он является DAG. Flow описывает возможные действия и допускает циклы. Reality хранит конкретные факты с причинными ссылками; каждая повторная попытка — новый узел. Порядок фактов задаётся серверной последовательностью. Координаты отделены от предметных связей.

**Последствия.** Можно безопасно менять раскладку без изменения статусов. Нельзя запускать задачу только потому, что карточка оказалась слева. Алгоритм Dagre может геометрически разложить циклический граф; поэтому запрет циклов проверяет домен до сохранения зависимости. Это наш вывод из требований Ouro, разделения процессной нотации BPMN и геометрических возможностей React Flow/ELK, а не требование этих библиотек.

### ADR-02. Отдельные состояния решения, исполнения и приёмки

**Контекст.** «Одобрено» двусмысленно: человек выбрал вариант, агент начал его выполнять или уже принят итог?

**Решение.** Статусы `DecisionRequest`, `Execution`, `Spec` и подтверждения DoD существуют отдельно. `resolved` означает зафиксированное человеческое решение. `running` возникает после подтверждения начала/возобновления. `done` требует актуальных доказательств и человеческой приёмки. Каждая команда проверяется таблицей переходов, ролью отправителя и guards.

**Последствия.** Интерфейс показывает несколько коротких подписей вместо одного вводящего в заблуждение цвета. Одобрение не вызывает неявный запуск; ответ не закрывает другие блокирующие запросы. Подход использует явные события/условия из SCXML и понятие human task из BPMN; конкретные переходы определяются [методологией Ouro](status-methodology.md).

### ADR-03. Неизменяемые события и воспроизводимые проекции

**Контекст.** После переподключения, повторной доставки и изменения спеки человек должен понять, по какому ожиданию действовал агент.

**Решение.** Событие получает постоянный ID, номер последовательности, автора и привязку к ревизии/попытке. Активная ревизия может изменяться новым событием; старые события сохраняют прежнюю ссылку. `requestId` защищает от повторного эффекта команды, `expectedVersion` — от решения по устаревшему состоянию. Проекция может быть пересоздана из журнала; replay не отправляет агенту команды повторно.

**Последствия.** Хранилище прототипа строится вокруг PostgreSQL и append-only журнала. Одних отключённых кнопок в браузере недостаточно: ограничения проверяет сервер/домен. Долговечность, атомарность и восстановление должны иметь отдельные проверки. Основание: Fowler Event Sourcing и Microsoft CQRS; форма контракта — предметное решение Ouro.

### ADR-04. Простая предсказуемая раскладка раньше сложной оптимизации

**Контекст.** Для первого графа зависимостей достаточно обычных карточек и одного направления чтения. Вложенные группы и сложные порты повышают стоимость интеграции.

**Решение.** React Flow + Dagre для простого DAG; направление предпосылка → зависимая спецификация. Перераскладка вызывается явно, после статуса камера не перемещается. Проверка графа выполняется собственной топологической сортировкой/поиском пути. ELK остаётся вариантом для составных графов и ортогональной маршрутизации.

**Последствия.** Нет заявления об оптимальном числе пересечений или производительности на больших графах без измерений. Переход к ELK оправдан, когда появятся реальные группы/порты и сравнительный набор схем. Источники: React Flow Layouting и Eclipse ELK Layered.

### ADR-05. Граф имеет равноправный табличный путь

**Контекст.** Мелкие линии, масштабирование и drag-only операции мешают управлять задачами с клавиатуры и на небольшом экране.

**Решение.** Список/таблица использует те же ID, статусы, фильтры и выбор, что и граф. Через форму можно выбрать концы зависимости без перетаскивания. Статусы имеют текст; очередь решений доступна отдельно. Системные изменения не перехватывают фокус.

**Последствия.** Доступность не делегируется библиотеке целиком; на каждой итерации проверяются формы и переходы клавиатурой. Основание: указанные критерии WCAG 2.2 и React Flow Accessibility.

## 4. Что проверять при дальнейшей разработке

| Проверка | Почему она нужна |
|---|---|
| Добавить обратную зависимость в цепь A → B → C | Домен должен отклонить C → A, пояснив цикл |
| Изменить статус или добавить событие | Выбор, фокус и масштаб сохраняются; нет автоматического fit-view |
| Ответить на один из двух блокирующих запросов | Исполнение остаётся в ожидании второго |
| Повторить ту же команду и затем отправить устаревшую версию | Первый повтор возвращает прежний результат, конфликт версии не создаёт новое решение |
| Получить `succeeded` от агента | Спецификация не становится `done` без приёмки человеком |
| Активировать ревизию r2 после результата по r1 | Прежние факты/решение остаются на r1, новая работа не подменяет старый контракт |
| Перестроить проекцию и повторно загрузить приложение | Получается согласованное состояние без повторной отправки внешних команд |
| Пройти сценарий без мыши и в табличном режиме | Все существенные действия доступны, смысл состояния не зависит от цвета |

Это перечень приёмочных сценариев, а не утверждение о пройденных тестах. При изменении реализации решение ADR пересматривается новой записью с причиной; ссылка на источник сохраняется рядом с применённым принципом.
