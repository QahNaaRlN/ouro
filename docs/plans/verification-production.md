## Проверки и поставка

На момент создания журнала объединённый код проходит отдельную квалификацию; результаты, commit и ссылки PR/CI добавляются по факту. Необходимы unit/integration, TypeScript, canonical schemas, независимая упаковка протокола, replay, production build и полные production browser checks с новым сценарием парных карточек. Миграции проверяются на отдельной копии исторической резервной копии, без открытия живой БД как второго экземпляра.

Слияния выполняются последовательно через проверенный PR в `dev`, затем PR `dev` → `main`, с проверкой точных версий веток. Зелёный CI исходной feature-ветки или её прежний локальный прогон не заменяют CI объединения.

## Состояние домена и облачная граница

03.11.2026: публичный A-record `ouroapp.ru` разрешается; HTTP возвращает `308` на HTTPS через Caddy. HTTPS у двух клиентов с обычной проверкой TLS завершается `TLS alert internal error`, до получения HTTP-ответа. Причина ещё не установлена; для диагностики нужны текущие конфигурация и журналы Caddy. Доступность DNS не равна готовности HTTPS или приложения.

В репозитории нет подтверждённой конфигурации действующей облачной установки. Запрошены существующий SSH-профиль/каталог либо путь к локальным параметрам; пароли и ключи в чат не требуются. Без доступа серверный деплой не объявляется выполненным.

Текущий `npm start` включает локальную demo-сессию. Для облака требуется отдельный запуск без неё, точный `OURO_PUBLIC_URL`, проверка Host/Origin/cookies за настоящим HTTPS proxy, почты, входа, изоляции пользователей, внешнего PostgreSQL и восстановления backup. Новый workspace интерфейс и verification observer/run сейчас требуют локального оператора и закреплённой папки; hosted accounts используют другой путь. Простой запуск за доменом не обеспечивает их функциональное равенство.

Playwright runner исполняет выбранный JavaScript тестов/config с правами процесса ОС. Фиксированные параметры не являются изоляцией ОС; предоставлять этот исполнитель обычным пользователям облака в процессе приложения нельзя. Варианты локального агента/bridge и отдельного изолированного worker описаны в [предложении local/cloud](../proposals/local-cloud-modes.md).

## Следующие решения

Модель синхронизации, перенос выбранных существующих проектов, привязка исторических авторов, разрешённые данные, offline-операции и device permissions согласуются отдельно по конкретному [предложению](../proposals/local-cloud-modes.md). Подготовка/слияние verification не загружает локальные проекты, исходники или ключи в облако.
