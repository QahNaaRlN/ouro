# Подготовка облачного Ouro

03.11.2026. Основание — поручение владельца включить verification через `dev` → `main` и развернуть Ouro на доступном `ouroapp.ru`. Согласованы автономный local и облачный проект с одним серверным журналом; первый hosted-проект новый, закрытый и пустой. SMTP настраивается по схеме Grace с отдельными реквизитами Ouro, которые предоставит владелец. Email первого владельца и секреты находятся только в приватных операционных материалах.

## Исходное состояние и сохранность

На сервере обнаружен snapshot Ouro alpha.11 без Git, старые образы и подготовительные файлы. Известные девять каталогов данных/backup Ouro, а также его контейнеры, сети и volumes отсутствовали; это ограниченная проверка, а не поиск всех данных на диске. Snapshot и старые образы сохраняются. Параметры/данные/ключи действующих локальных проектов не переносятся.

Порты 80/443 заняты действующим Caddy Grace. Его конфигурация содержит отдельный hook для сайтов Ouro, но активный HTTPS site на момент проверки был только у Grace. HTTP `ouroapp.ru` отдавал 308; HTTPS отклонял соединение до HTTP. Подключение нового site, проверка объединённого config и reload планируются отдельно; наличие файлов в этой ветке не означает выполненный reload или готовый TLS.

Владелец разрешил root SSH; вход существующим ключом и известным host key подтверждён, создан профиль `ouro-production` с backup прежней локальной конфигурации. Чужие services/data/secrets не заменяются. Сборка на действующем VPS не планируется: у него один CPU и около 1.6GiB RAM; image и реальная PostgreSQL квалифицируются в отдельной среде.

## Изменения подготовленного кода

- Отдельный hosted launcher требует HTTPS public origin и внешний PostgreSQL, запрещает local demo и общие human/agent credentials. Локальный launcher остаётся автономным.
- Текущий workspace UI поддерживает аккаунты и проверяемое членство. Owner/Contributor/Viewer определяют доступ на сервере; команды повторно проверяют текущую роль в транзакции. Локальные папки и OS observer/runner остаются отдельной возможностью доверенного локального оператора. Облачный аккаунт её не получает.
- Облачное подключение MCP не показывает серверные пути как локальные инструкции клиента. Контекст без привязки честно сообщает недоступность файлового контекста и server-owned observer/runner.
- Origin для JSON mutations сверяется с каноническим настроенным origin; регрессия внутреннего HTTP URL за публичным HTTPS proxy воспроизведена и исправлена. Неизвестные Host, чужой Origin и подмена forwarded headers не дают доступ.
- Production image включает текущие protocol, миграции 001–011, public assets и native-зависимости. Runtime работает под `node`; compose создаёт отдельную внутреннюю БД/сеть без published ports, а app подключается к существующей edge-сети отдельным alias.
- App использует PostgreSQL 17.11 и отдельный login без SUPERUSER/CREATEDB/CREATEROLE/REPLICATION/BYPASSRLS. Он владеет своей БД и её объектами для миграций; отдельный admin credential нужен только для настройки и backup/restore. CI проверяет именно ограниченную роль приложения.
- Bootstrap получает приватный файл и создаёт аккаунт и новый пустой project с Owner membership. Он отказывается автоматически повторять создание при уже существующих аккаунтах. Контейнерный `node` должен иметь доступ к строго выбранному mode600 input; общий secret mount не предоставляется.
- SMTP поддерживает отдельные host/port/secure/user/password/from и прежний URL. Неполные/неоднозначные настройки отклоняются, TLS certificate verification включена; для STARTTLS требуется успешное TLS-согласование. SMTP-секреты не встраиваются в image.

## Полученные проверки и открытые gates

Серверные HTTP-проверки облачного workspace прошли 5/5: роли, назначение и точный retry, foreign scope/participant/project, отзыв SSE-доступа, запрет OS capability, отсутствие серверных путей и прежний local-folder сценарий. Дополнительный набор multiproject/verification/legacy negotiation/history/proposals прошёл 27/27. Отдельные SMTP/launcher/health проверки — 4/4; auth/participant/login и HTTPS proxy — 18/18. TypeScript и сборка операционных модулей прошли. Итог production build и browser квалифицируются после общего freeze.

Эти результаты не подменяют следующие gates:

1. Реальный PostgreSQL: 001–011, ограниченная app role, concurrency/CAS, immutable history, receipts, account scope и полный custom-format dump/restore с проверкой всех строк и replay. Для этого добавлен отдельный обязательный CI job с disposable databases и явным подтверждением тестовых URL.
2. Свежий production image: запуск, health, native password hashing/login, работа под app384MiB/heap256MiB и db256MiB, сохранность после restart. Начальные limits не считаются достаточными до измерения.
3. Полный свежий CI объединения verification и облачной ветки; затем последовательные PR в `dev` и `main` с проверкой точных SHA.
4. Серверный новый instance, backup/restore, Caddy validate/reload, действительный TLS и проверка прежнего Grace до/после; отсутствие анонимного и межпроектного доступа.
5. Настоящие SMTP-реквизиты, TLS/auth/delivery и пользовательские сценарии приглашения/восстановления. Наличие parser tests не доказывает доставку почты.

Первые попытки запуска локальных Docker gates и загрузки диагностического CI artifact не были исполнены: автоматическая проверка разрешений возвращала `Selected model is at capacity`. Дополнительная batch-публикация тестов через GitHub получила timeout проверки; разрешённый повтор затем прошёл. Владелец указал продолжить подготовку кода/CI, а защищённые действия повторить позже. Эти ошибки не являются выводом о небезопасности команд и не обходятся. Позднее разрешение read-only Git fetch снова прошло; дальнейшие результаты записываются по факту.

## Эксплуатационные границы

Проверяемый локальный dump, checksum и isolated restore не означают готовые offsite backups, их шифрование, расписание, retention или согласованные RPO/RTO. Эти решения остаются открытыми. Откат приложения не откатывает миграции и не разрешает затирать новые записи старой копией.

Синхронизация, durable offline queue, кэш, перенос существующих проектов, device bridge и изолированный cloud runner не реализуются этим пакетом. Их принципы и оставшиеся решения — [local/cloud](../proposals/local-cloud-modes.md). Прежний [RFC статусов/контрактов](../proposals/status-contract-followups.md) остаётся на согласовании. [Runbook](../hosting-guide.md) описывает точные операции, а [журнал verification](verification-production.md) — отдельную интеграцию новой функциональной ветки.
