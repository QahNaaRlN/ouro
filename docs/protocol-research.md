# Предметный контракт Ouro · прочитанные источники и решения

29.10.2026. Исследование относится к ограниченному пакету [OURO-ENG-000013](specs/domain-contract.md): переносимый Flow, входы существующих MCP tools, ответы и отдельная установка. Выполненные проверки и их точные результаты находятся в [журнале](plans/domain-contract.md); этот документ не заменяет gate.

## JSON Schema: диалект и идентичность

Прочитаны разделы `$schema` и `$id` в [JSON Schema Core, Draft 2020-12](https://json-schema.org/draft/2020-12/json-schema-core).

- `$schema` определяет диалект и метасхему, а не версию продукта Ouro.
- `$id` задаёт идентификатор ресурса схемы. Он не обязан быть адресом доступного сетевого сервиса.
- Описание структуры не является проверкой полномочий, человеческого решения или реального результата работы.

Применение: canonical bundle объявляет Draft 2020-12 и стабильные URN с версией контракта, например `urn:ouro:protocol:0.1.0:flow`. Manifest перечисляет схемы и имена файлов. Внешний потребитель может работать с локальными JSON-файлами, без зависимости от размещения сайта Ouro.

Процессный граф сохраняет явные ссылки и типы. Идентичность узла не выводится из названия, координат или похожего текста. Достижимость, уникальность ID, ссылки и допустимые повторы проверяются семантически, как и прежде. Основания human task/choice и графовых правил остаются в [методологии диаграмм](diagram-methodology.md) и [исследовании графов](graph-research.md).

## MCP: контракт инструментов и фактическая совместимость

Прочитан раздел [MCP Tools, редакция 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools): discovery инструментов, `inputSchema`, `outputSchema` и structured results. Ссылка закреплена на редакции; `latest` со временем может указывать на другой текст.

Этот источник задаёт ориентир для предметного контракта. Он не означает, что установленный сервер автоматически поддерживает все transport-возможности редакции 2026. Реальная совместимость определяется закреплённым `@modelcontextprotocol/sdk` 1.32.2 и проверкой обеих сторон соединения.

В установленных файлах SDK прочитаны:

| Файл | Наблюдаемое поведение |
|---|---|
| [server/mcp.js](https://unpkg.com/@modelcontextprotocol/sdk@1.32.2/dist/cjs/server/mcp.js) | Публикует input/output schemas, выполняет handler перед выходной проверкой; при `isError:true` серверная проверка output пропускается |
| [client/index.js](https://unpkg.com/@modelcontextprotocol/sdk@1.32.2/dist/cjs/client/index.js) | При наличии `structuredContent` клиент проверяет его по объявленной outputSchema, включая error-ответы |
| [server/zod-json-schema-compat.js](https://unpkg.com/@modelcontextprotocol/sdk@1.32.2/dist/cjs/server/zod-json-schema-compat.js) | Для Zod 4 при отсутствии явно выбранного target использует Draft 7 |

Это объясняет два решения пакета.

Во-первых, canonical JSON Schema 2020-12 и MCP wire Draft 7 описываются отдельно. Совместимость не определяется по одному только номеру приложения. Внешняя JSON Schema-проверка должна использовать корректный диалект.

Во-вторых, первоначальная идея SUCCESS-only outputSchema отклонена. Одного чтения серверной ветки `if (isError) return` было недостаточно: настоящий SDK-клиент всё равно проверяет присутствующее structuredContent. Поэтому публичная outputSchema tool описывает обе ветви по `ok`, а отдельные SUCCESS/error схемы доступны для явного использования. При регистрации сохраняется корневой ZodObject, совместимый с SDK; discriminator/required-ветви присутствуют и в публикуемом JSON-представлении.

Ресурсы `ouro://protocol/manifest` и `ouro://protocol/schemas` добавляют discovery без нового tool. Stdio bridge проксирует resources только при объявленной удалённым сервером capability. Каталог статический и не содержит данных проекта; прочитать схему не означает получить назначение или право записи.

## Один источник структуры и сохранение семантики

До пакета runtime-проверка Flow существовала отдельно, а `draft.flow` в опубликованной MCP-схеме был `{}`. Входной JSON Schema описывал наличие поля, но не давал агенту формального словаря узлов и связей.

Применение: структурные определения, TypeScript-типы, Zod-проверка и JSON Schema получаются из переносимого пакета. Приложение использует его публичную скомпилированную форму, а не отдельную копию модели. Ручное редактирование сгенерированного JSON не становится вторым источником истины; `protocol:check` проверяет соответствие определениям.

Граница остаётся явной: конверт события описан, но `payload` и error `details` в версии 0.1.0 — JSON-расширения. Это не полный типизированный каталог событий и не готовый стандарт пакетной публикации всей дорожной карты.

Текстовые ограничения существующего Flow используют JS `string.length`, то есть UTF-16 code units; стандартная JSON Schema-проверка длины не полностью заменяет эти условия для astral-символов. Переносимый семантический валидатор сохраняет прежние ограничения Unicode/NUL, ссылок и графа. Изменение сериализатора не является основанием молча расширить или сузить допустимые старые ревизии.

## Ответ после commit и идемпотентность

Порядок вызова в SDK важен: проверка output происходит после handler, а значит, SQL-команда уже могла быть сохранена. Ошибка построения ответа или разрыв соединения не доказывают отсутствие записи.

Применение: безопасная предметная ошибка сообщает `outcomeUnknown:true`; исходные requestId/body сохраняются до выяснения результата. Клиент не должен превращать такую ошибку в новый business request. Квитанция и повтор проверяются отдельно от формы публичного ответа. Старые receipts остаются immutable; новые выходные схемы не требуют перезаписать историю.

Валидатор допускает дополнительные JSON-поля DTO ответов и сохраняет их. Входы и Flow остаются закрытыми. Это позволяет читать совместимые расширения ответа, сохраняя запрет на неизвестные входные команды; расширение схемы не предоставляет новых прав.

## Самостоятельная установка

Прочитаны разделы [Node ESM](https://nodejs.org/api/esm.html) о модулях и файловых URL; сборка и package metadata также проверяются непосредственно по исходникам пакета. Практические решения: самостоятельный npm-пакет, явные ESM/CommonJS exports и declarations, переносимые Node paths, JSON-файлы и CLI в tarball.

Библиотека зависит только от Zod. Next.js, SQL, UI, назначение агента и MCP transport принадлежат приложению или внешнему адаптеру. Это позволяет установить контракт в другом проекте, не перенося весь Ouro и его данные. Публикация в registry не заявляется: артефакт готовится через `npm pack`, отдельно устанавливается и проверяется.

Правила версий учитывают закрытые входы и Flow: добавление поля не всегда совместимо. До 1.0 несовместимые изменения требуют новой MINOR-версии; текущий клиент принимает точную явно поддерживаемую версию. Версия пакета не заменяет transport-версию MCP или schemaVersion старых событий.

Команды установки, CLI, discovery и восстановления описаны в [инструкции](protocol-guide.md), самостоятельные API — в [README пакета](../packages/protocol/README.md). Нативные Windows/macOS и сторонние языковые реализации не объявляются проверенными только на основании переносимого формата.
