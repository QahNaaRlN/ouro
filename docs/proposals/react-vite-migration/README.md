# Переход Ouro на React и отдельный backend

Статус: **архитектура и решения D01–D16 приняты владельцем 2026-11-04**. Реализация миграции **PAUSED_BY_OWNER с 2026-11-05**. По ретроспективе подготовлен [план завершения C0–C7](../../plans/react-vite-completion.md); его подготовка не возобновляет код и проверки. Принятый эпик: `codex/react-vite-epic`.

Принятая основа — React, TypeScript и Vite, самостоятельный Node.js/TypeScript backend и подготовка встраивания Ouro в Meridian с сохранением существующей функциональности. Все 16 рекомендаций согласованы владельцем. Последующее поручение разрешило реализацию в отдельном эпике через атомарные фича-ветки. Дополнительное обязательное требование — полная замена обычных собственных UI-стилей на Tailwind CSS 4 с сохранением внешнего вида и поведения. Первый срез и результаты ведутся в [журнале foundation](../../plans/react-vite-foundation.md); [HTTP baseline](http-baseline.md) фиксирует исходную границу сервиса.

## Основания и статус

Источник правил — текущие локальные файлы `.cursor/rules/*.mdc` в `C:/Work/cbs-core-frontend`. Их список и SHA-256 закреплены в таблице переноса. Нормализованные требования изложены здесь, поэтому дальнейшая разработка Ouro не должна зависеть от наличия этого пути на другой машине.

Архитектура и сценарии Ouro сверены с локальным исходным состоянием `c369079294939a7890567b129495aae34090968b`. Изучение исходников подтверждает состав перехода; оно не является новым результатом запуска приложения или приёмки. Реестр API содержит 47 файлов маршрутов Next, включая серверные обязанности, которые нельзя перенести в браузерную сборку.

Запись принятия и границы каждого решения находятся в [decisions.md](decisions.md). Документы сохранены по прежним адресам в `proposals`, чтобы не нарушать ссылки; действующий статус этого пакета — принятая архитектурная основа. Они задают требования будущей миграции Ouro. Настройка их автоматического контроля и доставки агентам относится к реализации; контракт текущего выпуска и статусы исторических проверок сохраняются отдельно.

TanStack Router выбран для web, i18next + react-i18next — для локализации, Temporal — для новых вычислений времени с проверкой runtime. pnpm workspaces выбраны основой разработки; Turbo подключается после описания фактического графа задач и cache inputs/outputs. Hono — принятый основной кандидат HTTP adapter, который должен пройти техническую квалификацию в P2; Fastify остаётся резервной альтернативой. Конкретные версии и настройки выбираются по совместимости. Дополнительные варианты инструментов, не выбранные в D01–D16, не становятся принятыми только из-за упоминания в сравнительной таблице стека.

## Архитектурные обязательства перехода

1. Правила hFSD защищают границы фронтенда проверками импортов и публичных API. Архитектура backend описывается через собственные обязанности и зависимости.
2. Предметные факты, авторизация, миграции базы, файловые операции и запуск проверок остаются на серверной стороне. Клиентское состояние не становится источником таких фактов.
3. React-интерфейс получает прикладные сервисы через явный контракт. HTTP, браузерное окружение и возможности Meridian имеют отдельные адаптеры.
4. Существующие данные, идентичности, права, версии, квитанции команд, совместные черновики и семантика протокола сохраняются по проверяемым сценариям.
5. Нативная интеграция имеет собственную границу проверки. Подготовка переносимого интерфейса не означает наличие готового host bridge или SSO.

## Как читать таблицу переноса

Слово «матрица» в первоначальном обсуждении обозначало сводную таблицу. Здесь используется более точное название — **таблица переноса правил**: её столбцы содержат разные свойства правила и текстовые решения.

Математически полезная матрица возникает, например, для отношения «правило × файл»: значение в ячейке обозначает применимость правила к конкретному файлу при заданном контексте. Эта структура помогает вычислять набор применимых правил. Она отличается от таблицы классификации и от результатов проверки исполнения этих правил. Учебный пример такого представления для размышления о Themis обсуждается отдельно от требований этого пакета.

## Условия начала реализации

Архитектурное согласование D01–D16 завершено; прежнее разрешение реализации было приостановлено владельцем. Для продолжения требуется отдельное поручение возобновить работу. После него перед каждым срезом фиксируется точная исходная версия и реестр сохранения поведения. Для каждого переносимого сценария указываются старый и новый владелец, ожидаемый результат и проверка. Оставшиеся технические допуски и упаковка имеют конкретные этапы C0–C7 и не требуют повторного выбора принятых рекомендаций. Изменение принятого решения или предметного поведения фиксируется отдельно.
