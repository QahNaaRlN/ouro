# Решения по противоречиям и адаптации стека

Статус: **D01–D16 приняты владельцем 2026-11-04**. Реализация начата в отдельном эпике и **RESUMED_C0 с 2026-11-05**. [Пересобранный план завершения](../../plans/react-vite-completion.md) меняет порядок и объём дублирующих проверок; содержание принятых решений сохраняется. Владелец отдельно возобновил реализацию по этому плану.

Основание принятия — прямое поручение владельца в этом чате: «Принимаю твои рекомендации по всем 16 решениям. Зафиксируй их в документации и приведи целевую архитектуру и план миграции в соответствие. Код пока не меняем».

Приняты рекомендации вместе с уточнениями из их обсуждения: команды Ouro обычно принадлежат features; проектная сессия имеет одного владельца живого состояния; неизвестный результат записи сохраняется и при повреждённом ответе; pnpm выбран для разработки, а Turbo подключается после описания графа задач. D16 закрепляет TanStack Router, Node.js + TypeScript и Hono с обязательной технической квалификацией. На момент принятия совместимость Hono ещё не была доказана; впоследствии transport, все47/59bindings и independent source-build прошли свои проверки. Это не меняет принятое решение и не означает production/native acceptance; текущие результаты — в [журнале](../../plans/react-vite-integration.md).

Каждый пункт ниже содержит принятое решение, обоснование и проверку. Рассмотренные альтернативы сохраняются как контекст; они не являются равноправным открытым выбором после принятия. Конкретные версии и конфигурации, технические эксперименты и результаты реализации фиксируются в соответствующих этапах [плана миграции](migration-plan.md).

Область действия — целевая архитектура и миграция Ouro. Принятие не изменяет правила CBS, полномочия Meridian или опубликованный выпуск. Последующее поручение владельца разрешило реализацию в эпике `codex/react-vite-epic` через атомарные фича-ветки. Дополнительно требуется полностью переписать обычные собственные UI-стили на Tailwind CSS 4. Результаты реализации фиксируются отдельно в [журнале foundation](../../plans/react-vite-foundation.md). Документ остаётся по прежнему адресу в `proposals` для сохранения ссылок.

## D01 Размещение мутаций

**Противоречие.** В `hfsd.mdc` детальные критерии разрешают entity mutation, а описание features обобщает все записи как их обязанность.

**Принято.** Entity может предоставлять низкоуровневую мутацию только одной сущности, затрагивающую её собственные query keys и не содержащую навигации, диалогов или других сценарных эффектов. Feature владеет пользовательским действием, взаимодействием нескольких сущностей и соответствующими эффектами UI. Составная серверная команда сохраняет свою атомарность на backend, даже если UI вызывает её из feature.

Простая entity mutation — разрешённый частный случай. Команды Ouro часто меняют общий snapshot, cursor и историю проекта, поэтому большинство из них остаются features. Внешне простое действие не разрезается на независимые entity-операции, если его контракт затрагивает несколько проектных представлений.

**Почему.** Это сохраняет более точный критерий источника и разделяет транспортную операцию и пользовательский сценарий. Отнесение всех операций записи к features создало бы повторяющиеся технические обёртки без новой ответственности.

**Проверка.** Архитектурные примеры разрешённой entity mutation и сценария feature; запреты импортов; тесты инвалидации и отсутствия UI-эффектов у entity API. Источник: `hfsd.mdc`, строки 56–61 и 105.

## D02 Композиция виджетов

**Противоречие.** Источник разрешает ограниченную layout-композицию widget → widget и позднее формулирует абсолютный запрет.

**Принято.** По умолчанию соседние widgets независимы; их собирает page. Обычная сетка с children остаётся универсальным layout-примитивом. Исключение widget → widget допустимо только для действительно повторяемой структурной композиции, которая использует публичные UI-контракты, не создаёт циклов и не оркестрирует чужие запросы или состояние. Конкретное исключение имеет обоснование и точечный allowlist; заранее исключения не создаются и разрешение для всего слоя не расширяется.

**Почему.** Такой вариант сохраняет полезную композицию оболочки и позволяет проверить границу исключения.

**Проверка.** Проверка графа импортов и отрицательный пример доменного widget → widget. Источник: `hfsd.mdc`, строки 140 и 471.

## D03 Владение запросами и состояниями Query

**Противоречие.** «Поднимать запросы как можно выше» и «один key означает один запрос» можно понять шире действительных гарантий. В таблице Query-правила `throwOnError` ошибочно отнесён к metadata.

**Принято.** Запрос вызывает ближайший ответственный владелец сценария или композиции. Для общего состояния Ouro это один владелец project session, snapshot adoption и SSE-подключения; виджеты получают представления одного подтверждённого snapshot через selectors/hooks. Независимые справочники могут иметь отдельные запросы. Размещение hook ближе к компоненту не создаёт второй источник общей проектной истории.

Query keys отражают источник, субъект доступа, проект и влияющие параметры; секреты в ключи не помещаются. Повторные подписчики разделяют кэш по ключу, а сетевые повторения определяются явно заданными freshness/refetch/retry-настройками. `throwOnError` — опция Query, собственные UI-флаги — типизированные metadata. Loading, disabled, paused, background refresh и stale data описываются отдельно: один `isPending` не является универсальным предписанием показывать скелетон.

**Почему.** Граница ответственности важнее высоты в дереве React. Кэш не заменяет политику свежести или изоляции контекстов.

**Проверка.** Смена проекта/пользователя не показывает чужой кэш; disabled query не создаёт бесконечный загрузчик; refetch не стирает пригодные данные. [API TanStack Query](https://tanstack.com/query/latest/docs/framework/react/reference/functions/useQuery).

## D04 Единственный владелец реакции на ошибку

**Противоречие.** Источник требует один основной UI-путь, но реализация показывает некоторые schema errors через toast независимо от boundary или `suppressToast`.

**Принято.** Для конкретной ошибки заранее выбирается основной путь: ошибка поля, локальный блок данных, boundary либо toast. Разные ошибки нескольких полей могут отображаться одновременно; согласованное состояние формы может дополнять объяснение поля. Ошибка контракта не обходит выбранный путь. `suppressToast` подавляет только уведомление; классификация и техническая регистрация продолжаются. Нормализатор — чистая функция `unknown → AppError`, без вывода и сетевых вызовов. Transport adapter переводит внешнюю ошибку в согласованный клиентский тип, а глобальная политика Query работает с этим типом. Обработка в cache callback сама по себе не заменяет сохранённую Query ошибку.

**Почему.** Двойные уведомления и зависимость диагностики от UI-флага устраняются явным владением. Чистый нормализатор можно повторно использовать в HTTP, IPC и тестах.

**Проверка.** Табличные сценарии query/mutation × тип ошибки × основной UI-путь: одно уведомление, корректный тип ошибки и самостоятельный вызов reporter. Источники: `error-handling.mdc`, строка 115; `create-query-client.ts`, строки 98–116 в исходном `packages/shared/lib/tanstack-query`.

## D05 Повторы команд и неизвестный результат

**Противоречие.** Источник повторяет некоторые mutations по умолчанию и не одинаково классифицирует все schema errors как неповторяемые.

**Принято.** Автоматический retry изменяющих команд по умолчанию равен нулю. Повтор возможен только по контракту идемпотентности операции с тем же устойчивым business request ID, неизменным телом и исходным контекстом авторства. Истёкшая сессия не создаёт нового автора для старого запроса. При потере либо повреждении ответа после возможной записи UI хранит состояние «результат неизвестен» и восстанавливает квитанцию предусмотренным способом. Ошибка схемы ответа после возможного commit не доказывает отказ команды; невалидный вход, отклонённый до записи, — отдельный случай. Отмена ожидания не доказывает отмену серверной команды.

Читающие запросы могут иметь ограниченный retry для явно временных транспортных/серверных сбоев. Ошибки схемы, отмена, нарушения доступа, validation и конфликт версии не повторяются автоматически как временные сбои. После обновления контекста повтор становится отдельным осознанным действием.

**Почему.** Повтор транспортного вызова не должен создавать второй предметный факт. Такое поведение уже существенно для черновиков, публикации, импорта и проверочных команд Ouro.

**Проверка.** Потеря ответа после commit, повтор с тем же ID, изменённое тело, смена участника, отзыв прав и повторное открытие квитанции. Основания: [совместные черновики](../../collaboration-guide.md), [прежний RFC моста](../meridian-native-bridge.md), исходный `create-query-client.ts`, строки 122–143.

## D06 Техническая регистрация ошибок

**Расхождение.** Правила описывают централизованное логирование и production monitoring. В просмотренной реализации имеются dev console logs в нескольких точках, а подключённого production pipeline нет.

**Принято.** Отдельный `ErrorReporter` принимает безопасное представление ошибки: код, серьёзность, operation ID, correlation ID и очищенный контекст. Raw body, ключи, cookie, персональные данные и полный документ не отправляются по умолчанию. Дедупликация относится к конкретному occurrence, а не ко всем событиям с одинаковым текстом. Клиент, backend, асинхронная задача и native bridge имеют явные точки capture. React boundary отвечает за ошибки отображения; обработчики действий и асинхронные операции охватываются отдельно. Безопасное пользовательское сообщение не содержит raw stack.

Первый этап реализации включает структурированные локальные записи и интерфейс подключения production sink. На backend это записи с заданными полями в управляемый вывод сервиса; их сохранение определяется конфигурацией запуска. Клиентский dev-вывод не объявляется долговременным журналом. Выбор внешнего сервиса, retention и доставка telemetry составляют отдельное решение, без включения сетевой отправки на этапе переноса. Сбой reporter не ломает пользовательскую операцию и не запускает бесконечное сообщение об ошибке самого reporter.

**Почему.** Диагностика, нормализация и уведомление имеют разные обязанности. Это позволяет сохранить полезные механизмы и не выдавать комментарий в коде за готовую наблюдаемость.

**Проверка.** Redaction, корреляция client/service/command, повторное сообщение об одном occurrence, независимые одинаковые ошибки и отсутствие секретов в клиентском bundle/логах. [Область React Error Boundary](https://react.dev/reference/react/Component#catching-rendering-errors-with-an-error-boundary).

## D07 Пустые и недоступные данные

**Противоречие.** Описание DataState и реализация различаются сигнатурой, набором empty-значений и видом предупреждения.

**Принято.** Использовать один тип результата `value | empty | unavailable`. Empty означает допустимые по контракту `null`/`undefined`; пропавшее обязательное поле является ошибкой схемы, а отсутствие данных до первой загрузки — loading. Пустые строки и массивы считаются empty только по объявленному контракту конкретного поля. `0` и `false` — значения. Сбой запроса либо схемы не превращается в empty. Состояния загрузки, обновления и устаревания сопутствуют данным отдельно; сохранённое значение может показываться с признаком неудачного обновления.

**Почему.** Отсутствие значения и невозможность получить значение требуют разных пользовательских действий. Универсальное превращение любого falsy-значения в пустоту теряет факты.

**Проверка.** Набор null, undefined, пустая строка, пустой список, 0, false, stale value, transport failure и schema mismatch. Контейнер вычисляет состояние; компонент отображения не знает HTTP/Query.

## D08 Локализация в React

**Противоречие.** `i18n.mdc` смешивает целевую систему registry/lazy loading, текущий другой набор locales, альтернативную библиотеку и несовместимые указания о регистрации переводов ошибок.

**Принято.** Для React выбраны i18next + react-i18next: namespaces по ответственности, типизированные ключи, явная загрузка и fallback, интерфейс перевода ошибок без глобального импорта UI. Переход сначала сохраняет действующие русские тексты Ouro. Новый язык, новый fallback и Weblate workflow оформляются отдельным расширением поведения. Общие UI-примитивы получают готовые строки; предметное состояние хранит коды.

**Почему.** Namespaces и типизация соответствуют намерению исходных правил; реализация не зависит от ещё не созданных Vue registries. Lingui рассмотрен как альтернатива с извлечением и компиляцией каталогов. Принятый вариант — i18next; переход к Lingui в будущем потребует явного изменения этого решения.

**Проверка.** Типизация ключей, загрузка namespace без дублей, сохранение текста ошибок, смена языка без повторной предметной команды. [React hook и namespaces](https://react.i18next.com/latest/usetranslation-hook), [типизация i18next](https://www.i18next.com/overview/typescript).

## D09 Время и даты

**Противоречие.** Общее Zod-правило допускает `Date`, а правило дат оставляет его только внешнему UI. Конкретные locale/timezone исходного проекта не являются контрактом Ouro.

**Принято.** Разделить instant, календарную дату и время с зоной. Внешние протоколы сохраняют согласованный ISO-формат. Для новых вычислений выбран Temporal через совместимый adapter; совместимость Node, браузера и WebView проверяется до выбора native/polyfill. `Date` допустим на границе UI-библиотеки. Миграция не меняет представление, точность, timezone и смысл существующих timestamps; форматирование использует заданные настройки и Intl.

**Почему.** Тип времени должен выражать предметный смысл. Автоматическая замена даты может незаметно изменить день или порядок событий.

**Проверка.** Round trip ISO, разные зоны, граница суток и переходы календаря, сохранение порядка событий и отображения истории. Vue V-Calendar не переносится в React.

## D10 Схемы и значения форм

**Противоречие.** Forms и Zod задают разные схемы именования; пример смешивает тип input и transformed output.

**Принято.** Имя схемы отражает слайс и роль: например, `CreateSpecFormSchema`, `CreateSpecRequestSchema`, `ProjectResponseSchema`. Повторяющееся имя сущности не добавляется ради шаблона. Производные типы объявляются рядом со схемой; `z.input` и `z.output` различаются явно. TanStack Form владеет входными значениями, а перед командой один определённый boundary получает проверенный output. Проверка ввода может повторяться; преобразование в отправляемый payload имеет одного владельца. Преобразования snake_case/camelCase добавляются только по реальному контракту транспорта.

**Почему.** Типы формы, предметное значение и payload не обязаны совпадать. Валидация через Standard Schema не означает автоматическую передачу transformed output в submit.

**Проверка.** Тест с отличающимися input/output и однократным mapping, server field errors и сохранением введённых данных при ошибке. [TanStack Form о schema output](https://tanstack.com/form/latest/docs/framework/react/guides/submission-handling).

## D11 Именование и документация кода

**Противоречие.** Core JSDoc показывает дублирующие TS-типы, более специальное правило их запрещает. Примеры index используют `//`, а общая норма требует JSDoc. Globs и проверки частично рассчитаны на Vue и пути без фактического покрытия.

**Принято.** Сохранить kebab-case папок, PascalCase React-компонентов, camelCase `use...` hooks, семантические суффиксы и явные named exports. Каждый слайс имеет public API без `export *` и исполняемой логики. Для JSDoc сохраняются русское описание ответственности, порядок тегов и полезные примеры; типы `@param`/`@returns` берутся из TypeScript, `@throws` объясняет класс и условие. Разделители index оформляются как `/** api */`. Технические директивы и generated files имеют точечные исключения. Новый source/test-код не получает blanket-разрешения `any`.

Проверки должны охватывать реальную структуру `.ts`, `.tsx`, `.mts`, `.cts`, aliases, относительные импорты и package exports. Старые отклонения учитываются отдельно; правило не разрешает самовольное массовое переименование. `use` обозначает настоящий React hook; чистый formatter им не становится. Каждый Vue `computed` не требует `useMemo`, а `watch` — механического `useEffect`.

**Почему.** Стандарт сохраняется вместе с намерением и проверяемостью. Случайный пример не создаёт исключение из более точной нормы.

**Проверка.** Fixtures положительных/отрицательных импортов и именования, проверка globs, TSX и отрицательный тест deep import. Источники: `jsdoc-core.mdc`, `jsdoc-ts.mdc`, `index-standard.mdc`, `naming-conventions.mdc`.

## D12 Документация и область правил

**Расхождение.** Источник сочетает `docs/tasks`, `.cursor/reports`, `.agent`, внешний канон CBS и GitLab-процесс. Ouro уже имеет собственные specs/plans/proposals и English Conventional Commits.

**Принято.** Использовать существующие разделы Ouro. Предложения отделять от принятых решений и результатов проверки; правило имеет область применения и источник. Переносимые требования излагаются самодостаточно в одном источнике, а Cursor rules, `AGENTS.md` и будущие адаптеры служат способами их доставки. Автоматическое применение правил к другому репозиторию, перенос Confluence/GitLab-владения и принудительная уборка исключаются. Этот документ является записью принятия D01–D16; прежний путь в `proposals` не отменяет его действующий статус.

**Почему.** Архитектурный стандарт должен переживать смену инструмента агента; процесс конкретного продукта не становится частью технологического стека.

**Проверка.** Рабочие относительные ссылки, отсутствие второго активного стандарта, точные scopes и сохранение текущих инструкций до отдельного включения новых правил.

## D13 Инструменты монорепозитория и версии

**Развилка.** Источник использует pnpm workspaces + Turborepo, а установленный сценарий Ouro опирается на npm, lockfile и автономный `npm run launch` из ZIP.

**Принято.** pnpm workspaces выбраны основой целевого репозитория разработки. Turborepo подключается под явно описанный граф задач с корректными cache inputs/outputs; его наличие не является предварительным условием hFSD или каждого этапа переноса. Переход инструментария выделяется в самостоятельный подготовительный этап с точным lockfile и проверками упаковки.

Пользовательский контракт `npm run launch` сохраняется до отдельного решения об изменении установки. Текущий launcher требует `package-lock.json`, выполняет `npm ci` и ожидает Next-specific readiness, поэтому совместимость обеспечивается отдельной работой над поставкой. Не оставлять два конкурирующих lockfile для одного дерева установки. При выбранной схеме упаковки отдельное release-дерево с собственным npm lockfile допустимо; оно должно воспроизводимо формироваться и проверяться независимо от pnpm-дерева разработки.

Версии React, TypeScript, Vite, TanStack, линтеров и native dependencies выбираются по проверенной таблице совместимости, с учётом Meridian и Windows. Переход на последний major не является условием миграции.

**Почему.** Это сохраняет предпочтение пользователя и не превращает архитектурный перенос в скрытое изменение поставки.

**Проверка.** Clean install, повторяемый build, сборка protocol package, автономный ZIP launch/restart, существующий data directory и Windows paths. Основание: [текущая инструкция запуска Ouro](../../first-release-guide.md).

## D14 Транспорт и полномочия Meridian

**Развилка.** HTTP-фронтенд и native WebView имеют разные модели доступа. Существующий RFC описывает две ограниченные операции, а не полный backend Ouro через IPC.

**Принято.** Прикладные порты определяют чтение, команды и подписки. Web получает HTTP adapter с сохранением same-origin cookie/session поведения. Meridian получает только согласованный ограниченный host adapter. Доступность операции проверяется явно; HTTP/fs/shell proxy общего назначения не появляется. Смена host context закрывает старые подписки, изолирует кэш и отклоняет поздние ответы по epoch. Результат уже отправленной команды учитывается даже после смены экрана.

Host credential не выводится из view handle; SSO и хранение секретов имеют самостоятельный контракт. Raw response и ошибки native транспорта нормализуются на границе. Подключаемая React-панель использует runtime и согласованные providers хоста без второго независимого приложения внутри него.

**Почему.** Единая клиентская модель не означает одинаковые полномочия или доступность полного набора методов во всех окружениях.

**Проверка.** Порты с разными наборами возможностей, отрицательные проверки прав, смена проекта во время запроса, отписка и UNKNOWN-команда. [Предыдущий RFC](../meridian-native-bridge.md) остаётся отдельным предложением; реальная Windows/WebView2-проверка необходима для native результата.

## D15 Проверка сохранения поведения

**Развилка.** Компиляция, новые unit-тесты и исторический PASS не доказывают эквивалентность нового приложения.

**Принято.** До переноса закрепить исходную версию и реестр сценариев. Старый и новый вариант проходят одни контрактные проверки на изолированных fixture-данных. Сохраняются ожидаемые результаты, коды ошибок, полномочия, события, SQL-эффекты и поведение UI. Существующие тесты переносятся с минимальными изменениями инфраструктуры; изменение ожидаемого результата требует отдельного объяснения. Unit/integration/browser/e2e разделяются по обязанности, а не формально по каталогу. Известные дефекты отмечаются отдельно; их исправление имеет собственный ожидаемый результат и не подменяет проверку переноса.

**Почему.** Поведенческая регрессия часто проходит typecheck и выглядит как допустимый рефакторинг в diff.

**Проверка.** Реестр с результатами и ссылками на evidence, целевые негативные сценарии и полный соответствующий этапу набор существующих регрессий. Новая native функция имеет отдельную приёмку; её отсутствие не скрывается web-тестом.

## D16 Клиентский router и HTTP framework

**Новый выбор.** После удаления Next нужны клиентская маршрутизация и серверный HTTP adapter.

**Принято.** Для web выбран TanStack Router: типизированные params/search, вложенные layouts и композиция с Query. Route loaders обращаются к одному QueryClient и не создают вторую конкурирующую базу серверного состояния. URL и browser history сохраняются; backend отдаёт SPA fallback только для разрешённых UI-путей, не для неизвестного `/api`. React Router рассмотрен как подходящая SPA-альтернатива; переход на него потребует изменения принятого выбора.

Backend остаётся Node.js + TypeScript, чтобы сохранить существующие серверные зависимости и SQL-логику. Hono выбран **основным кандидатом** для тонкого HTTP adapter благодаря Web Request/Response модели. Принятие закрепляет приоритет кандидата, но не заменяет проверку его совместимости: в P2 требуется техническая квалификация SSE, отмены, raw webhook body, cookie, body limits и остановки/фоновых задач до окончательного допуска адаптера и переключения backend. Подготовительная проверка transport boundary выполняется отдельной атомарной историей без подключения рабочего хранилища; она не заменяет полный gate P2.

Fastify остаётся резервной альтернативой, если квалификация выявит существенное несоответствие или подтверждённую потребность в иной серверной plugin/lifecycle-модели. Такой результат фиксируется и ведёт к явному изменению выбора, а не молчаливой замене framework. Типы framework не выходят за транспортный слой. Замена Next `after()` требует явного владельца фоновой обработки и ошибок, а не detached promise без наблюдения.

**Почему.** Это отдельные технические адаптеры с ограниченной ответственностью; предметное ядро и сервисные сценарии не должны зависеть от их выбора.

**Проверка.** Навигация по всем старым URL и deep link reload, raw-body подпись, отмена стрима, несколько Set-Cookie и восстановление фоновой обработки. [TanStack Router](https://tanstack.com/router/latest/docs/overview); [официальный Node adapter Hono](https://github.com/honojs/node-server).
