## 2. hFSD и публичные границы

Сохраняется направление зависимостей: `app → pages → widgets → features → entities → api → shared`. Это карта ответственности клиентской части; backend не обязан повторять frontend-слои.

| Слой | Ответственность |
| --- | --- |
| `shared` | Инструменты и UI без знания предметной области Ouro |
| `api` | Транспортная инфраструктура, получение конфигурации и реализация согласованных портов |
| `entities` | Представления сущностей, схемы, ключи, hooks чтения и простые операции над своей сущностью |
| `features` | Пользовательские действия и сценарии, orchestration, связанные изменения и их последствия |
| `widgets` | Самостоятельные блоки экрана, объединяющие нижние слои |
| `pages` | Композиция маршрута, нормализация параметров, состояния входа на экран |
| `app` | Bootstrap, providers, router, тема и оболочка конкретного окружения |

По D01 мутация допустима в `entities` как узкое исключение: одновременно работает с одной сущностью, изменяет только её область кэша и не требует навигации, отдельного UI-сценария или специфичного уведомления. Большинство фактических команд Ouro затрагивает project aggregate, его версию, связанное состояние и события; такие команды принадлежат `features`, а атомарность остаётся на backend. Исключение не разрешает разрезать одну команду проекта на независимые entity writes. Виджет получает данные через публичные hooks нижних слоёв и не создаёт собственный транспортный `api/`. Страница компонует сценарии, а не становится местом исполнения доменных мутаций.

Runtime-импорты между соседними слайсами одного слоя по умолчанию запрещаются. Между `entities` допустима необходимая связь типов через публичный API без runtime-зависимости. По D02 исключения для widget → widget заранее не создаются. Только конкретный доказанный структурный случай может получить точечный allowlist: публичные UI-контракты, отсутствие циклов и чужой query/state orchestration, явное обоснование. Остальная композиция нескольких сущностей или сценариев размещается на подходящем верхнем уровне; доменный код не переносят в `shared` ради обхода ограничения. Критерии исключения закреплены в [решениях D01 и D02](decisions.md).

Публичный `index.ts` содержит явные именованные реэкспорты, без `export *` и логики. Порядок групп: `api`, `model`, `utils`, `ui`, общий `export type` в конце; отсутствующие группы пропускаются. Внешний слайс не импортирует внутренние файлы соседа. Внутри слайса используются прямые относительные импорты, чтобы его собственный barrel не создавал цикл.

Вынос в отдельный пакет обосновывается устойчивым контрактом и реальным повторным использованием. Полезную локальную feature не требуется заранее превращать в общую библиотеку. Встроенная версия Ouro должна отдавать композицию хосту; владельцем общего desktop layout остаётся Meridian. Точное размещение пакетов — в [целевой архитектуре](target-architecture.md).

## 3. Семантика React вместо механического переноса Vue

Компонент имеет явный контракт props и callback-props; hook — ответственность за React runtime, состояние или подключение другого hook. Чистый форматтер, mapper или классификатор остаётся обычной функцией без префикса `use`. Чистые helpers определяются вне тела компонента или в соответствующем модуле своего слоя.

Производные значения вычисляются из текущих props/state. Их не копируют в отдельный state через effect. Осмысленное имя вычисления улучшает читаемость, но не требует обязательного `useMemo`: мемоизация используется по подтверждённой необходимости. Vue `computed` и React `useMemo` не являются взаимозаменяемыми конструкциями. [Назначение useMemo в React](https://react.dev/reference/react/useMemo).

Effect нужен для синхронизации с внешним источником: подпиской, DOM API, таймером или подключением окружения. Его зависимости, cleanup и отмена принадлежат одному владельцу. Vue watchers не переводятся в effects автоматически; сначала определяется, нужны ли подписка, обработчик действия или обычное вычисление. При смене проекта, источника или маршрута старый ответ не должен обновить новый контекст.

Hooks вызываются в стабильном порядке; инфраструктурный клиент не создаётся заново при каждом рендере. Повторное подключение в development должно корректно очищать ресурсы. DOM-зависимости выражаются через refs, явный anchor или API библиотеки позиционирования, а не через предположение о CSS-классе родителя.

Для самостоятельной веб-оболочки по D16 принят TanStack Router: типизированные route/search параметры, вложенные layouts и интеграция с клиентским кэшем. Выбор принят; зависимость и настройка ещё не установлены. Loaders могут подготавливать данные через общий QueryClient; самостоятельный второй кэш серверных сущностей в router не создаётся. Для встроенного entry навигацию предоставляет либо согласует Meridian; второй browser router поверх хоста не появляется автоматически. [Возможности TanStack Router](https://tanstack.com/router/latest/docs/overview).

## 4. TanStack Query: серверное состояние

TanStack Query отвечает за загрузку, кэш и синхронизацию серверных представлений. Эти данные не дублируются в глобальном UI-store или `localStorage`. Query cache не становится источником серверных фактов, прав доступа или подтверждением исполнения команды.

Функция транспорта остаётся независимой от React. Hook чтения или мутации живёт в `api/` своего слайса; отдельные hooks имеют отдельные файлы. Схема проверяет входящие данные до попадания в кэш. `select` и presentation helpers выводят нужное представление из уже проверенных данных и не исправляют нарушение контракта молча.

### Ключи и смена контекста

Ключи строятся типизированными фабриками и имеют иерархию для точечной invalidation. В ключ входят параметры, от которых действительно зависит результат: выбранный проект, provider/workspace/repository, идентификатор сущности, фильтры, пагинация, закреплённая редакция или scope, когда они меняют ответ. Это соответствует [правилу зависимостей query keys](https://tanstack.com/query/latest/docs/framework/react/guides/query-keys).

Контекст доступа разделяется устойчивой безопасной идентичностью или поколением сессии; секретный credential не включается в query key, лог или persisted cache. При смене пользователя или полномочий очищается либо изолируется относящийся к прежнему доступу кэш. Смена проекта отменяет ненужные запросы и подписки; проверка контекста ответа остаётся обязательной, если транспорт не гарантирует отмену.

Mutation keys обозначают вид операции, но не заменяют бизнес-идентификатор команды. Query key также не заменяет точные версии, hashes и tokens, обязательные в существующих контрактах Ouro или Meridian.

### Обновление и повтор

После подтверждённой команды обновляется или инвалидируется её известная область данных. Глобальное сбрасывание всего кэша не используется как стандартный способ скрыть отсутствие карты зависимостей. Поздний результат из прежнего проекта не инвалидирует новый проект по неполному ключу.

Принятый по D05 default для мутаций — **без автоматического retry**. Повтор разрешается отдельно для конкретной операции, когда определены её идемпотентность, неизменяемый идентификатор, тело, получение квитанции и восстановление неопределённого исхода. Потеря ответа не доказывает, что запись отсутствует. Нарушение схемы ответа после возможного commit также не доказывает отказ команды: результат остаётся UNKNOWN до предусмотренного восстановления квитанции, без автоматического повтора и выдуманного rollback. Поведение исходного шаблона с глобальным повтором мутации не переносится. TanStack Query позволяет управлять политикой повтора; библиотека не создаёт идемпотентность операции. [Мутации TanStack Query](https://tanstack.com/query/latest/docs/framework/react/guides/mutations).

Для чтения задаётся ограниченная политика временных сбоев с backoff. Нарушение схемы, отмена, отсутствие права и постоянная ошибка контракта не повторяются по общему правилу. Числа попыток, таймауты, `staleTime`, `gcTime`, refetch при focus/reconnect фиксируются после сопоставления сценариев; значения CBS не являются автоматическими defaults Ouro.

`isPending`, фоновое `isFetching`, отсутствие данных и ошибка различаются по смыслу. Hook отдаёт состояния, которые нужны потребителю. SSE, Yjs и восстановление совместного редактирования сохраняют собственные контракты: внедрение Query не заменяет их кэшем запросов.

По принятому D03 активный проект имеет одного владельца project session и SSE-подписки с общим проверенным project snapshot. Виджеты и features получают необходимые представления через selectors этого snapshot; они не создают параллельные SSE-потоки или независимые загрузки одного project aggregate. Владелец отвечает за смену context epoch, отписку, применение событий и восстановление соединения. Дополнительный endpoint вводится по реальной самостоятельной ответственности, а не ради искусственного entity-by-entity разбиения текущего ответа.

## 5. TanStack Form и Zod: вход, выход и владелец преобразования

Состояние формы представляет редактируемый **вход** схемы (`z.input`), а payload после преобразований — её **выход** (`z.output`). Производные от Zod типы объявляются рядом со схемой в `.schema.ts`; `.types.ts` содержит самостоятельные ручные типы. Схема отражает согласованный контракт: `.nullable()`, `.optional()` и defaults не добавляются ради сокрытия повреждённого ответа. [Входные и выходные типы Zod](https://zod.dev/basics).

Для формы задаются полные типизированные `defaultValues`; поля подписываются на нужные участки состояния через React API TanStack Form. Vue refs и шаблонные bindings не копируются. Повторное получение серверных данных не должно незаметно перезаписать незавершённый ввод; смена контекста и повторная инициализация формы получают явный сценарий.

Validators отвечают за обратную связь по вводу. Нельзя предполагать, что подключение схемы в validator автоматически передало её transformed output в `onSubmit`. В проверенной документации TanStack Form это отдельный шаг. [Обработка submission и transformed values](https://tanstack.com/form/latest/docs/framework/react/guides/submission-handling).

Для одного submission выбирается **один владелец преобразования** `FormInput → CommandPayload` на границе feature и её сервисного порта. Если mapper запроса выполняет parse, `onSubmit` передаёт ему вход, а не разбирает тот же payload второй раз. Нижний адаптер принимает согласованный тип выхода. Это смысл правила «parse один раз»: оно не запрещает повторную validation во время редактирования или независимую проверку недоверенного HTTP/IPC входа backend либо нативным хостом.

Ответ сервиса также проходит проверку своей схемой на клиентской границе. Существующие JSON Schema и протокол Ouro не переписываются автоматически на Zod: сначала устанавливается единый владелец wire-контракта и способ исключить расхождение схем.

Полевые ошибки сервиса связываются с полями по стабильным кодам; форма сохраняет введённые данные и различает ошибку поля, отказ команды и нарушение схемы ответа. Состояния pending, отмена, двойное подтверждение и неизвестный результат операции описываются отдельно. По принятому D10 имя схемы отражает слайс и роль без механического дублирования сущности: например, `CreateSpecFormSchema`, `CreateSpecRequestSchema`, `ProjectResponseSchema`. Исторические несовместимые шаблоны исходных rules не управляют новой реализацией одновременно.

## 6. Axios, сервисные порты и Meridian

Axios является HTTP-инструментом исходного стека и кандидатом для клиентского адаптера выделенного backend. Его применение не должно менять семантику текущих запросов Ouro: cookies/credentials, отмену, uploads, streaming/SSE, ошибочные ответы и восстановление соединения проверяют отдельно. Наличие Axios не требует заменить каждый работающий `fetch` в одном шаге.

Потребитель зависит от предметной операции сервисного порта, а не от `AxiosResponse`, HTTP URL или конкретного вызова Tauri. HTTP-адаптер получает конфигурацию из bootstrap. Встроенный адаптер Meridian получает только явно разрешённую часть контракта через согласованный host IPC; полный набор HTTP-возможностей ему не приписывается. Ему не нужен Axios, если он не выполняет HTTP. Порт не создаёт SSO, credential storage или новые host-права.

Семантические ошибки транспорта нормализуются в общий контракт. Проверка DTO, отмена, context binding и получение квитанции не исчезают из-за смены транспорта. Обёртка «выполнить произвольный URL/метод/файл» не является предметным портом интеграции. Точный native bridge остаётся отдельной областью [целевой архитектуры](target-architecture.md).

По D16 backend сохраняется на Node.js + TypeScript. Hono принят как **основной кандидат для проверки** тонкого HTTP adapter с Request/Response; это ещё не допуск его реализации к полному трафику Ouro. Проверяются SSE и отмена, raw webhook body, cookies, лимиты тела и принадлежность background jobs; замена Next after() требует явного владельца и обработки ошибок. Fastify остаётся fallback при неподходящем Hono adapter или более подходящем серверном lifecycle. Framework-типы не выходят за транспортный слой; выбор Hono не переносит прикладное ядро на него.

## 7. UI-состояние и персистентность

Начальная React-реализация использует локальный state, reducer и hooks по месту ответственности. Context допустим для стабильных зависимостей, конфигурации и ограниченного составного UI; запреты Vue `provide/inject` не становятся абсолютным запретом React Context. Выбор Redux, Zustand или другого общего store не сделан: он требует конкретного сценария, который не решается ясным локальным владением.

Общий store, если понадобится, хранит UI-состояние своего слайса: панели, табы, шаги мастера и выбранные режимы. Он не выполняет скрытые GET и не зеркалирует query cache. Передача данных между слайсами не маскируется глобальным реестром.

Разрешённая персистентность — явно нужные пользовательские настройки, безопасные идентификаторы продолжения и предусмотренные продуктом неопубликованные черновики. Формат получает namespace Ouro, версию, validation и миграцию. Существующие постоянные черновики Ouro сохраняются; правило не переводит их в RAM. Персистентный ответ API и credential не возникают автоматически из примеров Pinia/localStorage CBS. Политика сессии и секретов определяется отдельно для веба, сервиса и Meridian.

## 8. Стили, компоненты и модальные сценарии

По дополнительному поручению владельца обычные собственные UI-стили полностью переводятся на Tailwind CSS 4: global component rules, CSS modules и статические inline presentation styles. Переносятся существующие цвета, темы, размеры, типографика, responsive/focus/reduced-motion состояния. Текущие [глобальные стили](../../../app/globals.css) и [стили рабочего пространства](../../../components/workspace-styles.css) являются основанием паритета. Допустимый остаток узкий и объяснённый: theme/base/font declarations, необходимые keyframes, внешний library CSS и вычисляемая runtime-геометрия через CSS custom properties. Массовый перенос старых селекторов в `@apply` не закрывает требование. Временные legacy layers фиксируются как незавершённый остаток. [Интеграция Tailwind с Vite](https://tailwindcss.com/docs/installation/using-vite).

Base UI остаётся текущим набором примитивов Ouro; Vue-обёртки и отдельная UI-библиотека CBS не переносятся. Существующие React Flow, Lucide и редакторские зависимости сохраняются по своим сценариям. При сборке пакетов проверяется обнаружение Tailwind-классов в подключённых исходниках; глобальные reset/styles и тема встроенного модуля не должны менять оболочку Meridian.

Модальный сценарий имеет одного владельца открытия, данных и финализации. Presentation-компонент получает данные и сообщает намерения, а orchestration выполняет запросы и команды на своём уровне. Controlled React dialog совместим с этим принципом: наличие `open`/`onOpenChange` само по себе не является архитектурной ошибкой. Требование VFM «только dynamic useModal, никогда visible» — деталь Vue, которая не переносится буквально.

Крестик, Esc, backdrop и программное закрытие сходятся в одну точку завершения; callback и освобождение ресурсов исполняются один раз. Проверяются focus trap/restore, клавиатура, доступные названия и scroll lock. Закрытие окна не означает отмену уже принятой сервером команды. При сохранении черновика, переключении проекта и незавершённом действии требуется явный жизненный цикл, а не два параллельных флага видимости.

Layout без домена, навигационных решений и прав может быть общим UI-примитивом. Web shell и Meridian shell владеют своей навигацией и providers. Фиксированная ширина CBS, названия его приложений и sidebar не входят в переносимый стандарт.

## 9. Даты и время

Переносимое намерение исходного стека — неизменяемые временные значения, явная семантика даты и timezone, форматирование через Intl. По принятому D09 для новой логики используется Temporal: календарная дата и момент времени не заменяют друг друга. Данные wire-контрактов сохраняют существующий согласованный формат; переход библиотеки не изменяет значения, offset/timezone, точность и представление существующих timestamps. Сохранённые строки истории не пересериализуются автоматически только потому, что вычисление использует Temporal. [Модель Temporal](https://tc39.es/proposal-temporal/docs/).

Перед внедрением проверяются Node runtime сервиса, целевые браузеры, Windows WebView2, TypeScript definitions и сборка. Нативная доступность Temporal не предполагается по наличию свежего браузера разработчика. Необходимость и версия polyfill, размер сборки и способ загрузки решаются по этой проверке. Автоматическое обновление всех зависимостей или переписывание любых встреченных `Date` не разрешается этим документом.

Timezone берётся из явной продуктовой/пользовательской политики, locale — из выбранного языка интерфейса. `Europe/Moscow`, фиксированная `ru-RU` и формат «умного года» из примеров CBS не назначаются Ouro автоматически. V-Calendar исключён как Vue-специфичный UI; React calendar/date picker выбирается отдельным срезом при необходимости.

## 10. Локализация

Переносим статические типизированные ключи, владение namespace по слоям, таблицы соответствия доменных кодов сообщениям и отсутствие динамической сборки ключей из недоверенных значений. Runtime-объект ошибки или статуса сохраняет код; пользовательский текст выводится через адаптер выбранной локализации. Presentational shared/UI может получать готовые строки через props и не должен знать продуктовые namespaces.

Переключение языка имеет явные состояния загрузки/недоступности словаря, fallback и дедупликацию параллельной загрузки. UI-текст, plural rules и форматирование дат проверяются вместе. Текущие тексты Ouro сохраняются в миграции; добавление языков не является её автоматическим результатом.

Принятый по D08 React-адаптер — `react-i18next` + `i18next`: namespace ownership, загрузка нужных словарей и типизированные ключи соответствуют переносимому контракту. Выбор библиотеки принят; конкретные совместимые версии и подключение проверяются при реализации. Извлечение ключей, новые языки и workflow переводов не добавляются без отдельной необходимости. [React binding и namespaces](https://react.i18next.com/latest/usetranslation-hook), [типизация ключей i18next](https://www.i18next.com/overview/typescript).

Lingui сохранён в истории исследования как рассмотренная альтернатива; D08 уже выбрал i18next, поэтому выбора между ними в текущем плане не осталось. Vue I18n, различающиеся source-коды `kz/kk`, Weblate и обещанный registry не переносятся как подтверждённая действующая инфраструктура. Внедрение адаптера не активирует новые языки и не меняет действующий fallback Ouro. Каноническая запись принятия и будущая проверка находятся в [D08](decisions.md).

## 11. Ошибки, диагностика и деградация данных

Ниже раскрыт принятый по D04–D07 целевой контракт; его реализация NOT_STARTED. Он сохраняет смысл исходного стека и **не копирует** обнаруженные различия между rules и реализацией CBS.

### Общая ошибка и единственный владелец реакции

`unknown` нормализуется в общий `AppError`/error DTO с категорией, стабильным кодом, безопасным сообщением, критичностью и при необходимости field errors. HTTP, IPC, схема ответа и runtime получают согласованные классификаторы. Передача между процессами опирается на проверяемый DTO; `instanceof` локального класса не является межпроцессным протоколом.

Компоненты не разбирают `error.response.data` и не выбирают UI только по HTTP-коду. Для каждой операции назначается primary UI-path:

| Сценарий | Основная реакция |
| --- | --- |
| Ошибка ввода/поля | Ошибка рядом с полем, сохранение ввода |
| Отказ пользовательской команды | Контекстный feedback либо один глобальный toast |
| Недоступность дополнительного блока | Inline/fallback с сохранением рабочего экрана |
| Невозможность построить основной экран | Boundary или полноценное состояние ошибки |
| Ожидаемая отмена | Завершение без тревожного toast |
| Неизвестный исход записи | Явное неподтверждённое состояние и восстановление квитанции |

Глобальная и локальная реакции не дублируются. `throwOnError` остаётся верхнеуровневой опцией Query; оно не является полем `meta`. Если выбран boundary, глобальный cache не добавляет тот же toast. `suppressToast` имеет одинаковую семантику для query и mutation; исключение для schema mismatch не включается молча. Дополнительная диагностика не отменяет подавление пользовательского уведомления.

Нарушение схемы ответа — контрактная ошибка с нейтральным текстом, а не обычная ошибка пользовательского поля. Для изменяющей команды после возможного commit такое нарушение означает UNKNOWN до восстановления результата по D05; оно не объявляет серверную запись неуспешной. Его не скрывают nullable/coercion/default и не повторяют автоматически. Политика recovery зависит от класса ошибки; кнопка retry не рисуется безусловно во всех error states.

React boundary покрывает свою область ошибок рендера. Ошибки обработчиков, внешних async операций и подписок требуют собственных capture points; Vue `onErrorCaptured` не переводится в обещание универсального React перехвата. [Область ответственности React error boundary](https://react.dev/reference/react/Component#catching-rendering-errors-with-an-error-boundary).

### Нормализация и reporting — разные ответственности

По D04 нормализатор — чистая функция: классифицирует `unknown → AppError` и не выводит данные, не выполняет reporting, сетевые вызовы или UI-эффекты. Capture/reporting и выбранный UI-путь — отдельные ответственности, без зависимости нормализатора от toast, React компонента или провайдера мониторинга. Диагностический sink подключается явно в bootstrap и получает ограниченный event: код, операция, безопасный context, correlation/request/command identifier и допустимые сведения об источнике. Контракт redaction задаёт, какие поля разрешены; credentials, полный payload и содержимое пользовательского документа не пересылаются по умолчанию.

Пользовательское уведомление и диагностический event имеют отдельную дедупликацию. Повторный вызов нормализации из UI не должен повторно отправлять одно событие. Классификатор retry использует тот же смысл кодов, но сам не показывает toast и не выполняет reporting. По D06 отказ reporter/sink изолируется: не подменяет исходную ошибку, не изменяет результат команды и не вызывает бесконечное reporting собственной ошибки.

По D06 начальный sink — структурированная локальная регистрация с интерфейсом подключения production sink. Выбор внешнего сервиса, retention и отправка telemetry не включаются автоматически. В исходном CBS проверены normalizer, console logger для schema mismatch и toast service; описанная там отправка в production monitoring не подтверждена подключённой реализацией. В Ouro backend logging, renderer reporting и native reporting потребуют явных sinks и проверки доставки; наличие этого документа не означает готовой production observability.

### DataState и частичная доступность

По D07 принято единое типизированное различие `value`, `empty`, `unavailable`. Загрузка описывается отдельно и не показывается как «данных нет». `empty` означает допустимое отсутствие; `unavailable` — данные должны быть, но источник или контракт не позволяют их получить.

Контейнер вычисляет состояние и передаёт его presentation-компоненту; поле не разбирает transport error. `null`/`undefined` означают `empty` только там, где отсутствие разрешено контрактом поля. Отсутствие обязательного значения — ошибка контракта и `unavailable`, а не допустимая пустота. Поведение пустой строки и пустого массива задаётся явным predicate конкретного поля; ноль и `false` остаются значениями. Пустота не определяется общим truthiness check. Fallback не ломает layout и имеет понятные текстовые/доступные признаки состояния.

Существующие данные при неудачном background refetch и отсутствие данных при первой загрузке различаются. Возможность показывать сохранённый snapshot, признак его свежести и доступные действия задаёт сценарий; данные другого проекта не используются как fallback нового контекста. Восстановление выполняется на уровне блока, если повтор действительно способен помочь; оно не превращает UNKNOWN-команду в новый запрос записи.

## 12. Bootstrap и конфигурация

Bootstrap является местом сборки инфраструктурных зависимостей: проверенной конфигурации, выбранного HTTP/IPC адаптера, query client, локализации, темы, уведомлений и диагностического sink. Прикладной код получает готовые зависимости через явный runtime/ports контракт и не читает `VITE_*` самостоятельно.

Entry point только собирает runtime, подключает providers и монтирует корень. Секреты сервиса не включаются в конфигурацию renderer: `VITE_*` встраиваются в клиентский код. [Правила env Vite](https://vite.dev/guide/env-and-mode). Встроенный entry получает нужную конфигурацию от Meridian по согласованному контракту вместо скрытого чтения env браузерным пакетом.

Зависимости создаются один раз на нужную область жизни и освобождают listeners/subscriptions при завершении. Встраиваемый модуль не создаёт второй router, theme owner или глобальный query client поверх хоста без явного контракта композиции. Инициализация не выполняет доменные команды как побочный эффект импорта.

## 13. Именование, TypeScript и документация

Принятая по D11 React-конвенция сохраняет смысл исходной таблицы:

| Объект | Форма |
| --- | --- |
| Слайс/папка | `kebab-case`; feature — действие, entity — предметное понятие |
| Компонент | `PascalCase.tsx`, согласованный именованный экспорт |
| React hook | `useMeaningfulName.ts`; имя файла совпадает с основным экспортом |
| Query/mutation hook | `use…Query.ts` / `use…Mutation.ts`, один hook на файл |
| API/схема/ключи | `.api.ts`, `.schema.ts`, `.query-keys.ts`, `.mutations-keys.ts` |
| Mapper/formatter/константы | Осмысленный `.mapper.ts`, `.formatter.ts`, `.const.ts` |
| Чистое действие | Глагольное `kebab-case.ts` без ложного `use` |

Именование схем по D10, словарь suffix и public API по D11 приняты; их реализация в проверках и файлах впереди. Исторические source-конфликты и их разрешения зафиксированы в [решениях](decisions.md). Стандартизация имён не разрешает несвязанный рефакторинг. Стабильные protocol IDs, коды операций и публичные wire names не переименовываются вместе с папкой.

TypeScript `strict` сохраняется; `unknown` проверяется на внешней границе, а не превращается в `any` или непроверенный cast. Принятый по D11 запрет `any` для нового source действует и в тестах, без общего test override; сгенерированные и внешние файлы получают явную область применения. TS-конфигурации клиента, сервиса и общих контрактов имеют соответствующие runtime libs и не допускают случайный Node-only импорт в bundle WebView. Схема остаётся источником своих производных типов.

JSDoc публичного API объясняет назначение, наблюдаемое поведение, параметры, результат, реальные ошибки и существенный пример. Типы `@param`/`@returns` не дублируют TypeScript-сигнатуру; `@throws` указывает класс и условие. Русский язык исходного стандарта сохраняется для новых описаний этой документации; язык wire identifiers не меняется. Vue `@prop/@emit` и порядок SFC блоков заменяются документацией TS props/callbacks.

Для нового source/tests по D11 принята пользовательская конвенция описаний и разделителей через `/** … */`, включая короткие разделители вида `/** api */`, вместо обычных `//`. Необходимые директивы инструментов, generated code и существующие исключения рассматриваются явно в [решениях](decisions.md). Это не назначает массовую перепись старых комментариев и не требует бессодержательной шапки над каждым выражением.

## 14. Автоматическая проверка и тестовая политика

Правило считается обеспеченным, когда для него есть проверка и понятный результат. До включения целевого набора определяются совместимые TypeScript/React lint rules, проверка направлений импортов, отсутствие deep cross-imports, явность public API, naming audit, форматирование и проверка hooks/dependencies. Globs охватывают реальные `.ts/.tsx` пути клиента и пакетов; backend и сгенерированные схемы не попадают под frontend naming случайно.

Oxlint из исходного шаблона рассматривается как дополнительный инструмент только после проверки поддержки нужных правил и совместимости; он не считается заменой отсутствующей архитектурной проверки. Команды CBS, его exception allowlists, quality thresholds и scripts не объявляются существующими в Ouro.

Тесты разделяются по ответственности: чистые функции и схемы; взаимодействие модулей/адаптеров; React UI с providers; browser cases для настоящего DOM, focus и layout; критичные сквозные сценарии. Query/Form tests используют изолированные зависимости и проверяют успех, отказ и применимые edge cases. Ошибка схемы ответа, неизвестный исход команды, смена контекста и закрытие модального сценария являются наблюдаемым поведением, а не деталями реализации.

Для изменений поведения сначала фиксируется ожидаемый контракт и воспроизводимый тест, затем реализация и refactor. Покрытие не заменяет паритет: перечень существующих проверок Ouro и реальных пользовательских сценариев сохраняется в [плане миграции](migration-plan.md). Browser/WebView проверка не подменяется одним JSDOM-тестом; fixture и native evidence остаются различимыми. Не нужно дублировать каждую реализацию отдельным тестом только ради числа покрытия.

По D13 для разработки приняты pnpm workspaces. Turbo подключается после описания реального графа задач и корректных cache inputs/outputs; он не является условием архитектурного разделения. Переход оформляется отдельным этапом. Текущий `npm run launch` из ZIP требует root `package-lock.json` и выполняет `npm ci`, build и start; launcher также содержит Next-специфичное распознавание готовности. Сохранение этого consumer-контракта требует явной адаптации release-дерева, упаковки и запуска, а не обещания совместимости по названию команды. Один pnpm lockfile в development tree и отдельный npm lockfile самостоятельного release tree допустимы; конкурирующие lockfile одного дерева установки не создаются.
