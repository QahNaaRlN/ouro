В текущей структуре Next обслуживает страницы и 47 файлов `app/api/**/route.ts`. Серверные helpers находятся в `lib`; предметное ядро — `packages/core`; MCP — `packages/mcp`; переносимый протокол — `packages/protocol`; CRDT — `packages/collaboration`; контекст Meridian — `packages/meridian`. Эти границы уже позволяют переносить обязанности без переписывания предметной модели.

Внутри переноса не меняются предметные статусы, полномочия агента/человека, семантика событий, версия MCP-контракта или формат существующих данных ради новой структуры папок. Необходимое изменение поведения получает отдельный сценарий, решение и проверку. Текущий [RFC host bridge](../meridian-native-bridge.md) не превращается в реализованный нативный API при завершении web-миграции.

## Реестр сохранения поведения

До переноса каждый сценарий получает запись со следующими полями:

| Поле | Содержание |
|---|---|
| Сценарий и источник ожидаемого поведения | Понятное действие пользователя/агента и ссылка на spec/контракт |
| Исходный владелец | Страница, helper, HTTP route, store или фоновая задача |
| Целевой владелец | Слайс UI, application service, adapter, core |
| Предусловия | Пользователь, проект, права, версия, состояние подключения |
| Наблюдаемый результат | UI/HTTP/MCP-ответ, ошибка, событие, SQL-эффект, файл/квитанция |
| Неуспех и восстановление | Конфликт, потеря ответа, отмена, отзыв доступа, повторный вход |
| Проверка и данные | Существующий/добавленный тест, изолированный fixture, способ запуска |
| Результат | NOT_RUN, PASS, FAIL или BLOCKED и ссылка на фактическое evidence |

Набор проверок применяется к старому и новому сервису. Сравниваются семантически значимые результаты; недетерминированные timestamps/ID допускают только объявленные нормализации. Отличие не исправляется изменением expected под новую реализацию.

## P0 Фиксация поведения и подготовка

**Вход.** Поручение начать реализацию получено; исходная база зафиксирована в [SDD foundation](../../specs/react-vite-foundation.md). Текущая inventory-проверка охватывает [47 routes / 59 explicit methods](http-baseline.md).

**Работа.** Завершить реестр сценариев, инвентарь 47 маршрутов и UI URL. Для каждого маршрута закрепить method, path, auth, body/response, статус, headers/cookies, ограничения, background effects и владельца. Перевести принятые D01–D16 в проверяемые import graph, scopes и критерии конкретных срезов. Составить таблицу совместимости версий и fixture-план данных; принятие инструментов не заменяет проверку их версий, конфигурации и поведения в целевом runtime.

**Отдельный подготовительный toolchain-срез.** pnpm workspaces приняты как основа разработки; их настройка отделяется от переноса транспорта и предметной логики. Сначала закрепляются package boundaries, зависимости задач и действующие способы запуска. Turborepo подключается только после определения фактического task graph, зависимостей задач, cache inputs/outputs и влияющих env/resources. Задания с побочными эффектами не получают кэширование как обычная сборка. Совместимость потребительского `npm run launch` имеет собственный срез P5; текущая связка `npm ci`, `package-lock.json` и Next readiness не объявляется автоматически совместимой с новой workspace-структурой.

**Выход.** Все исходные маршруты и семейства имеют целевого владельца. Контрактные fixtures готовы, исходные проверки выполнены с известными результатами и ограничениями. Зафиксированы совместимый toolchain и реальные команды; для Turbo есть определённый граф и cache contract либо его подключение ещё не выполнено. Отдельно отмечены исторические FAIL/SKIP и существующие недостатки: они не объявляются исправленными новой миграцией.

## P1 Независимые контракты и архитектурный контроль

**Работа.** Выделить прикладные порты и транспортные DTO. Переиспользовать `@ouro/protocol` по его действующей области; UI-specific read models не объявлять автоматически публичным MCP API. Разделить shared primitives, frontend и server exports. Описать composition roots, конфигурацию, ошибки, capability и lifecycle подписки. Устранить обратные зависимости core/host на уровне контрактов с сохранением семантики импортов Meridian.

Владение командами следует D01: большинство команд Ouro изменяет общую историю/версию проекта и принадлежит feature-сценарию, а не произвольно объявленному CRUD entity API. Entity mutation допускается только при выполнении всех принятых критериев собственной сущности, своих keys и отсутствия сценарных эффектов.

Описать одну project session на объявленный project/identity/context scope: она владеет принятым snapshot, adopter, одной SSE-подпиской и их жизненным циклом. Query получает принятые данные этой сессии; отдельные экраны не создают независимые источники проектной истории. Read/command/SSE ответы проходят общую проверку монотонности и принадлежности контексту.

Зафиксировать классификацию и реакцию ошибок по D04–D07: normalizer чистый; технический reporter и пользовательское уведомление имеют отдельных владельцев. Сбой/отказ reporter не меняет результат исходной операции, не блокирует её завершение и не создаёт рекурсивную цепочку reporting. `empty` означает только разрешённое контрактом отсутствие; `null` в обязательном поле остаётся нарушением схемы, а не успешной пустотой. Ноль и `false` сохраняются как значения.

Добавить целевые проверки import graph, public API, browser/server boundaries и naming. Проверки покрывают aliases и относительные пути, а не только удобные примеры. Для старого кода допускается конечный список известных отклонений с владельцем; новый код не увеличивает его.

**Выход.** Core/протокол импортируются без React, Next, HTTP framework или Node-only UI-зависимостей; браузерный entry не втягивает store/credentials/child_process. Позитивные и отрицательные архитектурные fixtures подтверждают реальное действие правил. Проверены общий session/adopter contract, независимость reporting от исходного результата и различение допустимого отсутствия и schema mismatch.

## P2 Выделение backend и единственного владельца базы

**Работа.** Собрать `apps/service` с явным lifecycle, путями конфигурации/SQL-ресурсов, auth и routes. Сохранить Node/PGlite/PostgreSQL, существующую доменную логику, HTTP/MCP-семантику и server-side проверки. Устранить зависимость от Next request context и `after()`; фоновая обработка получает владельца, ошибки и shutdown/recovery.

Hono принят основным кандидатом для технической квалификации HTTP adapter Node.js/TypeScript сервиса. До закрепления его как основной реализации проверить SSE и отключение клиента, отмену, точные raw webhook bytes, несколько `Set-Cookie`, body limits, фоновые jobs и штатную/аварийную остановку. Fastify — fallback при подтверждённой недостаточности основного кандидата по этим критериям, а не свободный повторный выбор framework. Результаты квалификации фиксируются отдельно от факта принятия D16.

До переключения живого хранилища новый сервис работает только с отдельными fixture-копиями. Старый Next остаётся единственным владельцем рабочего PGlite. После полного контрактного сравнения выполняется согласованное переключение всех серверных обращений: сервис становится единственным владельцем БД, старые route wrappers при необходимости только проксируют в него. Нельзя переносить семьи маршрутов по одной, оставляя два процесса store на одном каталоге PGlite.

Старый Next UI может временно использовать сервис через ограниченный HTTP proxy. Прокси сохраняет cookie, streaming, auth-relevant origin semantics, raw webhook bytes и отмену; он не подставляет доверенные forwarding headers из пользовательского ввода. Серверные guards живут в сервисе, не только в proxy.

**Выход.** Все 47 маршрутов имеют эквивалентного владельца сервиса; контрактные проверки проходят на PGlite и предусмотренном внешнем PostgreSQL-профиле. HTTP adapter прошёл описанную техническую квалификацию. Startup не принимает предметные записи до готовности миграций; shutdown освобождает stream/timers/workers/DB. Switch/restart сохраняет события, версии, авторство и квитанции. Если PostgreSQL-профиль или обязательная проверка adapter не выполнены, это явный незакрытый результат, а не общий PASS.

## P3 React и Vite как самостоятельный клиент

**Работа.** Создать web entry, bootstrap и providers, выбранный TanStack Router с прежними URL, API adapter и QueryClient. Route loaders используют общий QueryClient, не создавая второй кэш проектных сущностей. Общая project session/adopter из P1 владеет проектными данными при навигации; screen hooks только подписываются на её представления. Во время разработки `/api` направляется на service; production service/reverse proxy обслуживает SPA и API в согласованной same-origin модели. SPA fallback не перехватывает отсутствующие API или assets.

Переносить экранные семейства отдельными срезами: каталог/вход → рабочий dashboard/roadmap → детальный процесс/проверки → участники/подключения → совместные черновики и дополнительные панели. Каждому срезу соответствует завершённая вертикаль: transport validation, Query/Form, UI state, ошибки, доступность и regression checks. Временная совместимость со старым UI не создаёт второй backend.

По дополнительному обязательному поручению владельца весь обычный собственный CSS переводится в Tailwind CSS 4 utilities: global component rules, CSS modules и статические inline presentation styles. Срезы включают legacy `/` и обе оболочки приложения. Временные legacy layers и оставшиеся старые selectors учитываются как незавершённый объём, а не готовая конверсия. Разрешён только объяснённый технический остаток theme/base/fonts, необходимых keyframes, внешнего library CSS и вычисляемой runtime-геометрии. Визуальный gate проверяет размеры, цвета, responsive layout, фокус, модалки, reduced motion и graph interactions.

**Выход.** Все старые UI URL открываются напрямую и через навигацию. Сохраняются ссылки, фокус, клавиатурные действия, история и предупреждения о несохранённом вводе. Нет зависимости новой сборки от Next runtime, server-only imports или генерации страниц сервером.

## P4 Живые данные и повторы

**Работа.** Подключить SSE через subscription adapter общей project session; подтвердить единственного владельца snapshot, adopter, подписки и обновлений Query на scope. Cursor/high-water mark и gap recovery сохраняют существующий протокол. CRDT controller владеет Yjs document, очередью и relative positions отдельно от query cache. При смене пользователя/проекта отписывать старый контекст и отбрасывать поздние ответы; незавершённые команды сохраняют сведения для восстановления результата.

Автоматический retry команд равен нулю. Потеря ответа, timeout, отмена ожидания и невалидная response schema после возможного commit переводят исход в UNKNOWN до предусмотренного восстановления. Schema mismatch ответа команды не доказывает, что запись не состоялась. Повтор использует прежние business request ID, тело и исходную identity по контракту операции; новое намерение не подставляется как технический retry.

**Выход.** Нет двойных stream subscriptions, конкурирующих snapshot owners или повторных предметных команд из-за React remount/StrictMode. Offline/reconnect/out-of-order updates, публикация после потерянного либо невалидного ответа, logout в соседней вкладке и навигация с непринятым текстом проходят парные проверки старого/нового поведения. Независимые сбои reporter не изменяют проверяемый исход команды или состояние восстановления.

P4 выделен для общей проверки cross-screen lifecycle; базовые подписки и recovery не откладываются из каждого среза P3 до конца проекта.

## P5 Поставка и consumer compatibility

**Работа.** Проверить принятую основу pnpm workspaces и подготовленный toolchain-срез P0 в реальной поставке. Turbo применяется только к определённому графу с проверенными cache inputs/outputs, отдельно от consumer installer. Сохранить потребительский `npm run launch` самостоятельным совместимым срезом: текущие `npm ci`, `package-lock.json`, сборка и ожидание Next readiness заменяются или адаптируются явно под состав нового релиза. pnpm workspace lockfile сам по себе не делает этот consumer-сценарий рабочим; у release installer должен быть собственный согласованный install/build/start contract без конкурирующих lockfile одного дерева установки.

Паковать статический UI, service, SQL/resources и переносимый protocol; пути вычисляются от установленного пакета/конфига, не случайного cwd. Если сохранить прежний публичный запуск технически невозможно, это фиксируется как изменение поведения со своим решением и проверкой, а не как незаметная часть смены менеджера пакетов.

**Выход.** Clean install/build, standalone protocol consumer и Windows ZIP `npm run launch`/restart проходят проверку независимо от dev workspace. Проверены launcher readiness сервиса/UI и владение дочерними процессами. Существующая БД открывается без seed/reset и без потери доменных данных; backup/restore проверены на изолированной копии. Старый релиз продолжает иметь пригодный обратный путь в рамках неизменённой схемы.

## P6 Основа интеграции Meridian

**Работа.** Экспортировать подключаемый React entry без собственного browser root/router и с явными зависимостями context/theme/navigation/services. Контрактные doubles проверяют разные capabilities, смену проекта, отсутствие host, ошибки и UNKNOWN. Они демонстрируют переносимость интерфейса, а не работоспособность native bridge.

**Выход основы.** Embedded entry не зависит от Next, не раскрывает credentials и не импортирует Node server. Тот же сценарий можно подключить через согласованный порт с ограниченным набором операций. Неизвестная/недоступная capability отображается явно.

**Отдельный native пакет.** Реальные команды host, credential provisioning, packaging, Windows/WebView2 acceptance и SSO не реализованы и не проверены этим планированием; они остаются отдельной работой с собственной областью проверки. Две операции из прежнего RFC не объявляются достаточными для всего Ouro. Принятые D01–D16 определяют основу встраивания, а не готовность host bridge.

## P7 Удаление Next и завершение миграции

**Работа.** После паритета удалить временные proxies, Next entry/config/dependency и связанные generated artifacts; обновить документацию запуска, CI и release scripts. Сохранить standalone npm/MCP/protocol интерфейсы по принятому контракту поставки и результатам P5. Выполнить весь соответствующий финальной поставке regression набор, не только последние затронутые тесты.

**Выход.** В исполняемых исходниках/зависимостях нет Next. Обычные собственные UI-стили полностью переписаны на Tailwind CSS 4; старые component CSS/modules, статические inline presentation styles и временные legacy layers отсутствуют. Технические исключения перечислены и проверены. Все записи реестра имеют фактический результат и evidence; незакрытые ограничения видны явно. Web-миграция, техническая native-подготовка, реальная host-интеграция, приёмка владельцем и выпуск имеют отдельные статусы.

## Проверки по этапам

| Уровень | Что доказывает |
|---|---|
| Static и architecture | Типы, scopes, запреты импортов, server/browser границы, отсутствие Next в целевом runtime |
| Unit | Чистый core, schemas, mapping, error/retry/DataState classifiers, key factories; разрешённый null против нарушенного контракта; независимость результата от сбоя reporter |
| Integration | SQL-транзакции, авторизация, HTTP/MCP, cookies, raw body, миграции, event/receipt semantics |
| Browser | Реальное взаимодействие React, Query/Form, focus, history, модалки, единственная project session, reconnect и CRDT; UNKNOWN после невалидного ответа команды |
| Package/runtime | Чистая установка, Windows paths, независимый launch, restart, owned processes, существующие данные |
| Native | Реальный Meridian/WebView2/IPC и назначенные capabilities; doubles не дают этот результат |

Фактические команды берутся из выбранной версии репозитория и её package scripts. Замена `tsx --test` на Vitest не должна менять expected ради удобства нового runner; оба набора могут временно существовать для разных обязанностей. Тесты с mock transport не доказывают HTTP/stream поведение.

## Обратный переход и данные

План не предусматривает изменения SQL-схемы ради замены web framework. Перед переключением сервиса сохраняются подтверждённая копия данных и параметры запуска. При откате новый процесс закрывается; прежний backend получает тот же каталог только после освобождения единственного владельца. Сравниваются доменные fingerprints, курсоры, ревизии, регистрации и квитанции.

Если новый срез всё же требует необратимой миграции данных, прежний способ отката больше не заявляется: нужен отдельный план миграции/восстановления и проверка на копии. Рабочие пользовательские данные не используются как fixture-площадка.

## Критерий завершения

Переход считается технически завершённым, когда самостоятельные React/Vite UI и backend сохраняют весь согласованный реестр поведения, действуют архитектурные проверки, подтверждена поставка с существующими данными и удалена runtime-зависимость от Next. Новые языки, внешний monitoring, полный native bridge и SSO имеют собственные задачи и не скрываются общим словом «готово».
