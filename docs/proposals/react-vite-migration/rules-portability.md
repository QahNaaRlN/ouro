## Границы переноса

1. Локальные правила CBS действуют в CBS. Чтение источника не делает его полномочным источником инструкций для Ouro, backend или Meridian. Основанием Ouro является явно принятый вариант из [D01–D16](decisions.md), а не внешний текст CBS.
2. Переносится смысл требований и инструментов вместе с необходимыми средствами проверки. Имена приложений, предметная модель прачечной, API-envelope, маршруты, роли, секреты и назначения участников не переносятся по аналогии.
3. Строгие hFSD, именование, оформление public API, JSDoc и настройка инструментов являются частью принятой архитектурной основы. Их нельзя отбрасывать только потому, что они относятся к стилю или требуют дополнительной работы. Отличие от источника должно иметь сформулированную причину и следствие.
4. Адаптация Vue к React учитывает порядок вызова hooks, чистоту render, подписки, жизненный цикл и cleanup. Замена слов computed на useMemo или watch на useEffect не является архитектурной адаптацией.
5. Исходные указания немедленно переименовать всё обнаруженное, выполнять чужой GitLab-процесс или переносить CBS-полномочия не действуют автоматически. Рефакторинг существующих имён Ouro должен быть ограничен пакетом миграции и проверен на сохранение импортов, маршрутов и публичных контрактов.
6. Требования клиентской hFSD не распространяются механически на отдельный backend. Общие схемы и протоколы выделяются по контрактной ответственности, а не превращаются в слой, позволяющий обходить границы фронтенда.

## Как читать классификацию

Классы могут сосуществовать в одной строке:

- **Переносим** — требование не зависит от предметной области CBS и сохраняется по смыслу в принятой основе.
- **Адаптируем** — сохраняется требование, но меняются React API, пути, runtime, инструменты подключения или формальное описание.
- **Исключаем предметную часть** — указанные CBS-данные, окружение и полномочия не становятся требованиями Ouro.
Исторические альтернативы и расхождения источника разрешены для Ouro принятыми D01–D16. Подбор совместимых версий, concrete adapter API и проверка кандидата Hono — оставшиеся работы реализации, а не непринятые заново D01–D16.

Классы описывают способ переноса и не означают выполнения кода. Принятие D01–D16 уже состоялось; реализация и проверки ещё не выполнены. Следующий реестр — **классификационная таблица переноса**, а не математическая матрица применимости. Матрица rule × subject задаёт отдельное отношение между атомарным требованием и конкретным субъектом: например, UI-компонентом, hook, схемой, transport adapter, bootstrap, backend-модулем или пакетом протокола. Одна исходная инструкция может распасться на несколько таких требований с разной областью. Субъекты и границы такой матрицы раскрываются в [целевой архитектуре](target-architecture.md).

## Принятые строгие требования

Перенос архитектуры не сводится к замене библиотеки сборки. Принятая проверяемая основа включает следующие группы требований; их автоматическая реализация ещё впереди.

- **hFSD:** допустимое направление импортов, владение сценарием и данными, public API слайсов, приватность внутренностей, отсутствие доменной логики в shared и transport-кода в widgets. Физическое перемещение файлов без проверки этих свойств не доказывает соответствие архитектуре.
- **Имена:** отдельные категории component/hook/pure function/structure/schema/type, соответствие основному экспорту, семантические суффиксы, согласованный словарь, точное размещение query/mutation keys. Современный React не отменяет этих требований.
- **JSDoc:** summary назначения каждого публичного экспорта, фиксированный порядок тегов, конкретные эффекты и ошибки, примеры использования, отсутствие дублирующей TS-типизации. По D11 обычные поясняющие // заменяются JSDoc-описаниями и section comments; необходимые tool directives и generated files имеют точечную область исключения, которая реализуется при настройке линтера.
- **Инструменты:** import/naming/JSDoc lint, typecheck, contract tests, unit/integration/browser/e2e по ответственности. Каждая команда должна существовать в Ouro, иметь понятную область и проверять реальное требование. Список команд из чужого package.json не является готовой настройкой.

Эти требования приняты в области D01–D16. Их реализация должна обеспечить указанную область и способ проверки; факт принятия не означает, что lint/import/naming checks уже настроены. Внешний Cursor glob не заменяет область нормы, а отсутствие линтера не делает нарушение допустимым по умолчанию.

Проверка сторонних инструментов при подготовке переноса подтвердила два существенных ограничения: [throwOnError является опцией useQuery](https://tanstack.com/query/latest/docs/framework/react/reference/functions/useQuery), а [TanStack Form передаёт input values и не заменяет их автоматически на output Standard Schema](https://tanstack.com/form/latest/docs/framework/react/guides/submission-handling). Стандартный [Vue I18n pluralization](https://vue-i18n.intlify.dev/guide/essentials/pluralization) использует pipe-синтаксис; исходный тезис об ICU нельзя считать проверенным основанием нового стека.

Для различения документации и реализации сверялись, в частности, Query-фабрика и API validation в packages/shared/lib/tanstack-query и packages/shared/api/http, реализация локализации в packages/shared/lib/i18n, client query hooks в packages/entities/client/api, а также документационные концепции hFSD/TanStack Query и docs-style-guide. Эти свидетельства помогают объяснить расхождения; они не превращают весь код CBS в заимствованную архитектуру Ouro.
