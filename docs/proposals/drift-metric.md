# Предложение: как измерять дрейф ожидания

28.10.2026 · редакция 1 · **формула согласована пользователем 28.10.2026; реализация следующим пакетом по дорожной карте**.

Пользователь попросил предложить формулу для отдельного согласования и затем явно принял её с указанными ограничениями. Этот документ фиксирует решение для будущей реализации по SDD/TDD; наличие согласования само по себе не означает готовую функцию. Основание: [ТЗ §5–6](../TZ-Ouro-OS.md), [ТС: история и ревизии](../TS-Ouro-OS.md), [статусная методология](../status-methodology.md).

## Рекомендуемый показатель

Предлагаю назвать основной показатель **«Изменено исходных ожиданий»**, а пояснение — «дрейф утверждённого объёма». Он отвечает на конкретный вопрос человека: **какая доля уже утверждённых спек была затронута изменением ожидания за выбранный период?**

Это показатель изменения требований. Он не измеряет качество агента, степень выполнения, потерянное время, семантическую близость к цели или долю неправильных действий. Человек может обоснованно изменить цель после полезного исследования; такая работа всё равно увеличит показатель изменения ожиданий. Причина и оценка последствий читаются по исходным фактам, а не выводятся из процента.

Предлагаемая идентичность алгоритма после согласования: `expectation-impact/v1`. Сейчас это имя проекта формулы, не действующая версия API.

### Формула и границы

Окно измерения задаётся двумя committed cursor: `W = (c0, c1]`, где `0 ≤ c0 ≤ c1`. Нужен полный журнал до `c1`, включая данные для восстановления состояния в `c0`; только событий внутри окна недостаточно.

`B` — неизменная исходная когорта: ID спек выбранного проекта/явного списка, у которых в проекции на `c0` есть активная ревизия и состояние не `invalidated`. Принятые по DoD спеки включаются: их ожидание тоже может быть позднее изменено. Черновики без активной ревизии в `B` не входят. Список `B`, его ревизии и зависимости фиксируются вместе с отчётом; изменение фильтра создаёт другой отчёт.

`I ⊆ B` — уникальные спеки исходной когорты, для которых внутри окна случилось хотя бы одно из следующих событий:

1. `RevisionActivated`, и контракт этой активированной ревизии отличается от исходного утверждённого контракта в `c0`.
2. `SpecInvalidated`: человек снял исходную цель с дальнейшей работы.
3. Изменился набор обязательных предпосылок `depends_on`, направленных в эту спеку. В текущей реализации это `DependencyAdded`; при появлении операции удаления потребуется явно расширить определение и версию алгоритма.

```text
N = |B|
K = |I|
Изменено исходных ожиданий, % = 100 × K / N, если N > 0
```

В отчёте первым показывается **«K из N исходных спек»**, затем процент с одним десятичным знаком. Диапазон — 0–100%. Одна спека с десятью изменениями входит в `K` один раз. Если внутри окна ожидание изменили и вернули к исходному, спека остаётся затронутой: возврат не стирает случившееся изменение. Частота изменений выводится отдельным счётчиком.

Спеки, впервые активированные после `c0`, не меняют знаменатель и не входят в числитель. Они показываются рядом как **«Добавлено новых утверждённых спек»**. Поэтому рост объёма виден, но не смешивается с изменением исходного объёма. Новые черновики без активации считаются отдельно. Новая связанная спека не выдаётся за изменение прежней без соответствующего события прежней спеки.

### Что означает «отличается контракт»

Для v1 предлагаю сравнивать структурно поля `goal`, `dod`, `constraints`, `assumptions`, `risks`, `inputs`, `flow` и набор обязательных зависимостей. Название и комментарий не входят в этот набор; их изменения показываются в истории, но сами по себе не увеличивают показатель. Технические ID ревизии, её номер, время, автор и parent не сравниваются как содержание.

Правило сравнения должно быть детерминированным: одинаковый порядок ключей объектов; критерии DoD сравниваются по стабильному `id` вместе с `text` и `required`; узлы и рёбра Flow — по `id` со всеми предметными полями и `entryNodeId`; зависимости — как множество ID предпосылок. Порядок элементов этих множеств и координаты холста не считаются изменением. Строки нормализуются только по переводу строк и краевым пробелам. Иные текстовые изменения, включая уточнение формулировки, считаются изменением — семантическую эквивалентность алгоритм не угадывает.

Отсутствующий optional `flow` у старой ревизии означает «схема не задана» и допустим для сравнения. Добавление схемы считается изменением ожидания. Это не доказывает, что прежняя работа была неправильной. Если позже потребуется исключать редакционные изменения либо отдельно оценивать существенность, нужна явная классификация человеком и новая версия алгоритма; LLM не должен незаметно решать это за него.

### Веса и интерпретация

Каждая исходная спека имеет вес 1. Размер, цена изменения и трудность задач не известны из текущего журнала, поэтому коэффициенты риска/сложности не вводятся. Показатель зависит от того, насколько крупно команда делит работу на спеки. Сравнивать разные проекты или команды по этому проценту без одинаковых правил декомпозиции нельзя.

Порогов «хорошо/плохо», красной оценки агента и автоматического запрета работы в v1 нет. Много изменений может означать нормальное уточнение задачи, изменение приоритетов или техническую проблему; источник причины открывает человек. Отклонённый вариант, новый Question, ожидание ACK и неудачная попытка сами по себе не меняют числитель. Отсутствие evidence не трактуется как доказанная ошибка.

## Воспроизводимый отчёт и проверяемые количества

Каждый отчёт хранит/возвращает: версию формулы, project/scope, `c0`, `c1`, исходные spec/revision IDs, `K`, `N`, вычисленное значение либо причину отсутствия, список затронутых спек и ссылки на события-основания. Для изменения ревизии показываются исходная и новая ревизии и изменившиеся поля. Необходимый diff вычисляется по immutable snapshots; события не изменяются.

Период в датах — подпись к cursor-границам. По умолчанию предлагаю сравнение от явно выбранного сохранённого baseline до текущего cursor. «За неделю» допустимо только при зафиксированном правиле выбора границ и показе фактического интервала; время внешнего агента не заменяет серверный порядок. Даты отображаются в часовом поясе пользователя. Reconnect и повтор `requestId` не создают дополнительное изменение, потому что расчёт идёт по committed событиям.

Рядом с основным показателем нужны отдельные количества, каждое со списком оснований:

| Количество | Точное содержание | Что не следует из него |
|---|---|---|
| Смены активной ревизии | `RevisionActivated` внутри окна, если до события у спеки уже была другая активная ревизия; первая активация отдельно | Число ошибок агента |
| Новые утверждённые спеки | Уникальные спеки вне `B`, впервые активированные внутри окна | Изменение каждой исходной спеки |
| Снятые исходные цели | Уникальные спеки `B` с `SpecInvalidated` внутри окна | Удаление истории или доказанная бесполезность работы |
| Замещённые запросы | Количество `DecisionSuperseded` внутри окна; это запросы, не уже принятые решения | Число ошибочных ответов человека |
| Открытые вопросы/развилки/блокеры | Снимок `pending` по видам на `c1`, с ревизией и blocking scope | Процент отставания или провала |
| Поздние факты прежнего контракта | `ActionReported` с явным `historicalContext: true` внутри окна | Несанкционированная работа: это может быть допустимая поздняя доставка |
| Факты без привязки к узлу Flow | `ActionReported` и `DecisionRequested` без `flowNodeId` внутри окна, отдельно для ревизий со схемой и без неё | Нарушение плана: ссылка optional, legacy-факты допустимы |

Последний счётчик применим после появления optional Flow-привязки. До её реализации он не изображается работающей телеметрией. Если схема есть, долю непривязанных фактов можно впоследствии выделить как показатель **полноты трассировки**, но нельзя складывать её с дрейфом ожидания в один процент.

## Нет данных, примеры и ограничения

| Ситуация | Результат |
|---|---|
| `N = 0`, журнал полный | «Нет исходной утверждённой базы», значение `null`, не `0%`; новые активации показываются количеством |
| `N > 0`, никто из `B` не затронут, журнал полный | `0 из N · 0,0%` |
| Не хватает части журнала/ревизии/истории зависимостей либо нет права читать запрошенный scope | «Недостаточно данных», значение `null`; частичный числитель не выдаётся за полный |
| Только новый черновик или предложенная, но не активированная ревизия | Основной показатель не меняется; предложения отдельно |
| Задержка обновления клиента | Отчёт явно ограничен `c1`; свежесть показывается отдельно, не скрывается процентом |

**Пример 1.** В `B` десять спек. У A активирована изменённая r2 и затем исходное содержание возвращено r3; у B изменён DoD; C инвалидирована. Добавлены две новые утверждённые спеки. Получается **3 из 10 · 30,0%**, три смены ревизии, одна снятая исходная цель, две новые утверждённые спеки. Возврат A и новые спеки не меняют знаменатель.

**Пример 2.** В `B` четыре спеки. Агент задал шесть вопросов, человек выбрал три варианта, одна попытка завершилась ошибкой, но ожидание и обязательные предпосылки не менялись. Получается **0 из 4 · 0,0%**. Вопросы и ошибка видны отдельными фактами; 0% не означает, что работа хорошая или завершена.

**Пример 3.** В `B` две спеки; для A добавлена обязательная предпосылка, у B изменён только комментарий. Получается **1 из 2 · 50,0%**. Малая когорта видна в подписи; процент не получает автоматический сигнал тревоги.

**Пример 4.** В исходной точке нет активных спек, затем активированы пять. Получается **«Нет исходной утверждённой базы»** и **5 новых утверждённых спек**. Подставлять 100% или 0% не предлагается.

Перед реализацией по SDD/TDD нужны сценарии: повторная доставка/один `requestId`; смена и возврат ревизии; несколько изменений одной спеки; неизменённое содержание в новой ревизии; изменение только title/comment; перестановка DoD/Flow без изменения содержания; новая спека вне когорты; инвалидация; обязательная и необязательная связь; zero denominator; gap/недоступная ревизия; исторический cursor; отчёт по иной версии/когорте. Результат должен воспроизводиться после reopen без записей в предметную историю.
