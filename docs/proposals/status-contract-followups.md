# Предложение: правила продолжения и недостающие контракты

03.11.2026. **Для согласования. Не реализовано и не активировано.**

Пользователь разрешил закрыть UI-пункты №13, 17, 19, 21 и 22. Этот документ отдельно описывает изменения, затрагивающие доменные правила, совместимость клиентов или локальный мост. Принятие дизайна и выполнение UI-пакета не означают согласования этих изменений.

## 1. Когда разрешать продолжение после решения

Сейчас положительное resolved-решение позволяет человеку разрешить продолжение, а агенту подтвердить resume до отдельного факта применения, если остальные guards выполнены. При завершении строгого шага Question/Fork требуют appliedAt; Blocker требует одобренный план и clearedEvidence, без универсального требования DecisionApplied. Это действующее поведение движка; порядок resume закреплён тестом `positive unapplied decisions do not add a UI-only resume barrier`.

**Рекомендация:** для новой согласованной политики сделать обязательный порядок для блокирующего запроса той же попытки и ревизии:

1. Человек записал положительное решение.
2. Для Question/Fork агент подтвердил применение именно текущего решения. Для Blocker подтверждены одобренный план и фактическое устранение с evidence; отдельное дублирующее подтверждение применения не предлагается делать обязательным.
3. Все остальные человеческие и физические блокировки сняты.
4. Человек отдельно разрешил продолжение.
5. Агент подтвердил возобновление. Только после этого исполнение становится running.

| Ситуация | Предлагаемое поведение |
|---|---|
| Решение pending или отрицательное | Продолжение зависимой работы запрещено. |
| Положительное Question/Fork-решение, применения ещё нет | «Решение принято; ожидается применение». Resume пока недоступен. |
| Решение применено, но физический Blocker не устранён | Продолжение запрещено до отдельного clearance/evidence. |
| Применение и блокировки проверены, разрешения человека ещё нет | Доступно отдельное разрешение продолжения. |
| Разрешение есть, ACK ещё нет | «Продолжение разрешено; ожидается подтверждение агента». |
| Пришёл ACK, guards всё ещё выполнены | running. |

Неблокирующий Question не останавливает независимую разрешённую работу. Текущие линии исправления/замещения решений, scope, активная ревизия, зависимости, stopRequested и неизвестная внешняя остановка продолжают проверяться. Remediation сохраняет существующее исключение своего устраняемого Blocker: иначе новая проверка заблокирует саму работу по устранению. Остальные блокировки remediation не обходит. Отзыв запроса не заменяет устранение физического препятствия. Успех попытки по-прежнему не принимает DoD за человека.

**Совместимость:** не переписывать старые события и не менять результат их replay. Рекомендуется сохранять версию политики в immutable-факте нового человеческого назначения; отсутствие версии означает legacy. Уже выданные разрешения и незавершённые попытки не переключать молча. Потребуются согласованные engine guards, контекст доступности MCP, версии DTO/schema и проверки старого/нового профилей. Подтверждение применения должно оставаться разрешённым во время ожидания человека, иначе получится взаимная блокировка «нельзя применить без resume — нельзя resume без применения».

**Нужно согласовать:** нужен ли этот обязательный порядок; вводить ли его только для новых назначений либо предусмотреть явный человеческий перевод незавершённых попыток. До согласования сохраняется текущий порядок.

## 2. Предложения уровня проекта

Сейчас AgentProposal всегда имеет исходные spec/revision/execution. UI может показать связанные предложения у спеки, но не может достоверно создать самостоятельное проектное предложение.

**Рекомендация:** отделить целевую область предложения от его происхождения. Добавить явную цель `project` или `spec`, сохраняя исходное разрешённое исполнение, автора, sourceCursor и sourceEventIds как происхождение. Старые записи получают прежнюю смысловую цель «исходная спека» при чтении, без переписывания истории. Проектная цель не попадает в счётчик конкретной спеки и сама не создаёт, не активирует и не запускает новую спеку.

Право агента отправить предложение по-прежнему основано на человеческом назначении и принадлежности проекту. Источники проверяются сервером. Предложения вообще без разрешённого исходного исполнения потребовали бы отдельной модели полномочий; рекомендую не включать это в первый шаг.

Потребуются типы proposal/команды, MCP input/output schemas, события и проекции, генерация протокола и тесты совместимости. Проверки должны покрыть два проекта, смену ревизии, старых клиентов и отсутствие расширения полномочий.

**Нужно согласовать:** достаточно ли проектной цели при сохранённом исходном исполнении или действительно требуется создание предложений без назначения агенту.

## 3. Достоверный тип MCP-клиента

Для фирменных значков нельзя угадывать клиент по имени регистрации.

**Рекомендация:** явное необязательное поле типа клиента в новой регистрации; известные профили Cursor, Claude Code, Claude Desktop и ChatGPT, а также unknown. Существующие записи сохраняют unknown. Тип — описательная информация, не подтверждение установки, online-связи или полномочий. Обновятся API регистрации, хранение, DTO и формы; при необходимости миграция добавит только nullable/unknown-поле.

**Нужно согласовать:** состав профилей и допустимость редактирования метаданных существующей регистрации человеком.

## 4. Выбор абсолютного пути к файлу ключа

Браузер не сообщает абсолютный путь через обычный file input. Ручной ввод остаётся рабочим поведением.

**Рекомендация:** при появлении локального desktop-моста добавить отдельный запрос системного выбора файла, возвращающий только путь. Выбор не читает содержимое ключа, не загружает его на сервер и не регистрирует доступ. Мост должен проверять допустимый origin/сеанс; пользовательская отмена отличается от ошибки. Для удалённого браузера вводится путь именно на машине MCP-клиента.

**Нужно согласовать:** нужна ли такая функция и какой существующий доверенный desktop-хост её предоставляет. Новый мост в UI-пакет не включён.

## 5. Структурированные причина и результат событий

В текущем UI показываются только уже записанные типизированные поля. Свободный evidence не превращается автоматически в подтверждённую причину, результат или причинную стрелку.

**Рекомендация:** расширять конкретные event payload только при наличии реального источника полей, с версией схемы и проверками на запись. Причинная связь остаётся явным идентификатором события, а не совпадением текста или времени. Старые записи читаются без выдуманных дополнений. LLM-сводка, если понадобится, должна быть отдельной интерпретацией с provenance, а не новым фактом истории.

**Нужно согласовать:** какие типы событий действительно требуют новых полей. Для завершения №22 расширение не требуется: уже имеющиеся reason/outcome выводятся в краткой записи.

## Порядок после согласования

Каждое принятое изменение получает отдельные критерии, совместимость и миграционный план, RED/GREEN-проверки и независимый обзор. Приоритет предлагается такой: правило продолжения; проектная цель предложений; client metadata. Desktop-мост и дополнительные payload-поля — только при подтверждённой потребности. До согласования ни один из этих контрактов и guards не меняется.
