# Предложение: локальный Ouro и ouroapp.ru

03.11.2026. **Базовая модель согласована владельцем: автономный local + облако с одним журналом проекта.** Синхронизация, кэш, offline drafts, устройство-мост и перенос полномочий этим документом не реализованы; их детальные контракты требуют отдельного согласования. Текущую интеграцию verification и облачную эксплуатационную приёмку следует оценивать отдельно. Прежние [статусные и контрактные предложения](status-contract-followups.md) остаются на согласовании.

## Рекомендуемая модель

Выбор режима принадлежит проекту. Одна установка сможет показывать локальные проекты и явно подключённые облачные проекты, сохраняя видимую границу между ними; такой общий каталог ещё не реализован.

| Режим проекта | Авторитетные данные | Работа без сети |
| --- | --- | --- |
| Автономный локальный | PGlite на компьютере, один процесс на каталог | Полная текущая локальная работа без аккаунта и облака |
| Облачный | Один последовательный журнал проекта в PostgreSQL на сервере | В первом выпуске требуется сеть; будущие кэш чтения и черновики — отдельный пакет |

Для облачного проекта локальная копия не становится вторым источником решений. Назначение, разрешение продолжения, изменение доступа, активация ревизии и приёмка требуют подтверждённой серверной записи. Локальные проекты не публикуются при входе в облачный аккаунт автоматически.

Основание: [store](../../lib/store.ts) выбирает PGlite или внешний `pg`, но не реплицирует их. [Движок](../../packages/core/src/engine.ts) требует последовательных версий одного проекта; [SQL](../../db/migrations/001_initial.sql) сохраняет immutable events/revisions, receipts и outbox. Это основа надёжной доставки, но не готовая двусторонняя offline синхронизация.

## Что можно выпустить первым

1. Интегрировать проверенную функциональную ветку через `dev → main`, сохранив отдельный отчёт совместимости с UI. Не смешивать этот выпуск с реализацией предлагаемых здесь контрактов.
2. Развернуть один экземпляр существующего Next.js за Caddy и выделенную PostgreSQL. Node закреплённой проверенной версии; отдельный пользователь сервиса, постоянные данные вне каталога исходников, закрытый внешний доступ к БД и серверным секретам.
3. Применить миграции 001–011 на отдельной квалификационной базе; проверить внешний `pg`, повторный старт, транзакции, rollback, параллельные запросы, scope и восстановление backup. Проверки PGlite не заменяют этот этап.
4. Облачный запуск отделить от локального: [local-next](../../scripts/local-next.mjs) включает local demo. Для `ouroapp.ru` нужны выключенный demo-доступ, точный public URL, проверенные Host/Origin/HTTPS и Secure cookies, реальные аккаунты/членство, приглашения и доставка почты.
5. Выпустить online-сервис только для явно поддерживаемых сценариев. Автономную установку и её рабочую БД сохранить. GitHub-архив, локальное обновление и работающий hosted-сервис имеют отдельные результаты приёмки.

Официальное руководство [Next.js self-hosting](https://nextjs.org/docs/app/guides/self-hosting) рекомендует reverse proxy и отдельно описывает координацию нескольких экземпляров. Начальный один экземпляр — наше решение для сокращения эксплуатационной сложности; текущие локальные очереди, observer и rate-limit Map ещё не доказывают безопасное масштабирование.

На 03.11.2026 DNS `ouroapp.ru` указывал на `195.133.195.190`; HTTP отвечал 308/Caddy. Два клиента получили TLS internal alert на HTTPS. Причина не установлена; наличие DNS и HTTP redirect не подтверждает готовый TLS или приложение. SSH-профиль сервера на момент этой проверки не определён. [Caddy automatic HTTPS](https://caddyserver.com/docs/automatic-https) требует корректных DNS/конфигурации, доступных портов и постоянного хранилища сертификатов; фактический сервер нужно проверить отдельно.

## Различия функциональности, которые нельзя скрыть

- [Основной workspace boundary](../../lib/workspace-access.ts) сейчас допускает локального оператора, а аккаунты и memberships обслуживаются отдельными маршрутами. Hosted account не получает права локального оператора. Для равного облачного UI нужны явная авторизация и проверка каждого project endpoint, команд, SSE и управления агентами.
- Протокол кандидата verification — `@ouro/protocol` 0.3.0, миграции 010/011 добавляют его хранение/runtime. Совместимость клиентов и восстановления проверяется для этой версии; прежний protocol 0.1.2 не объявляется автоматически совместимым. Версия архива приложения и версия протокола различаются.
- [Observer](../../lib/verification/observation.ts) читает выбранные файлы реальной локальной привязки. Сервер не видит папку на компьютере пользователя. Отсутствие входов означает недоступность/неизвестность, а не актуальный проверенный срез.
- [Local runner](../../lib/verification/local-runner.ts) запускает установленный Playwright с фиксированными аргументами на копии выбранных файлов. Загружаемые test/config — исполняемый JavaScript. Фиксированные argv, отдельная папка и сокращённое окружение не являются изоляцией ОС от файлов, сети или секретов пользователя процесса.
- В первом облачном MVP запуск пользовательского test/config в процессе/под пользователем приложения должен быть недоступен. Приём импортированного отчёта сохраняет его исходное происхождение и не становится `local_runner`/доверенным серверным прогоном. Облачный runner — отдельный пакет с изоляцией выполнения.
- Агент IDE/CLI может оставаться на компьютере с репозиторием и обращаться к облачному MCP. Возможности файлового контекста и server-owned runner при отсутствии привязки честно недоступны. Само подключение агента не выдаёт ему человеческие полномочия.

## Синхронизация и конфликты

Предлагаемый следующий слой — чтение committed событий облачного проекта по cursor с проверкой project scope, схемы, порядка и совместимости. Кэш показывает источник, подтверждённый cursor и время получения. Разрыв истории, rollback cursor или неизвестная версия требуют восстановления/обновления; старая картинка не называется актуальной.

[Yjs](../../lib/collaborative-drafts.ts) уже обслуживает совместные черновики. Его область — редактируемый текст/DoD с отдельной публикацией, а не решения, выполнение или authoritative журнал. Долговременное сохранение неотправленного текста при закрытии браузера сейчас не обещается; будущие offline drafts требуют собственного хранилища, восстановления и проверок закрытого/опубликованного черновика.

[Неподтверждённые команды UI](../../components/workspace-client.tsx) сейчас живут в RAM. Будущий durable intent сохраняет исходные actor/project/server/requestId, точное тело и expectedVersion. Таймаут или перезапуск не означают провал: сначала восстановление той же квитанции/точный повтор. Нельзя менять endpoint, автора, тело или версию под прежним requestId и нельзя автоматически направлять запрос в другую установку.

Сервер повторно проверяет актуальные права и CAS в транзакции. Конфликт версии показывает изменившуюся основу человеку; автоматическая подстановка latest version запрещена для смысловых решений. Отзыв доступа может запретить получение прежней квитанции — тогда исход остаётся неизвестным и требует разрешённой процедуры восстановления, а не нового действия.

Долговременная очередь не является разрешением выполнять всё позднее: устаревшее намерение сначала получает проверяемый исход. Новое действие после изменения основы требует отдельного подтверждения. При потере связи агент не считается физически остановленным; существующее разделение отзыва разрешения и фактического stop сохраняется.

## Явная публикация и перенос проекта

Публикация существующего локального проекта — управляемая миграция, а не копирование всей `.ouro`. Пользователь выбирает проект, сервер, получателей и состав передаваемых данных; до передачи видит объём, ограничения и чувствительные категории.

1. Проверить целевое владение, протокол/схему, активные исполнения и неизвестные исходы команд. Сначала разрешить неопределённость и остановить/подтвердить работы, мешающие переносу.
2. Создать проверяемую резервную копию; зафиксировать полный committed prefix, cursor, immutable revisions/hashes, receipts и связанные проверочные/административные факты. Перенос только событий недостаточен для доступа и дедупликации.
3. Импортировать в изолированный целевой проект с проверкой коллизий ID и полной сверкой. Сохранить исходные project/event/revision IDs, авторов, доказательства и происхождение; отображение прежнего local-human не выдаёт облачный Owner автоматически.
4. Новый Owner подтверждает привязку своей облачной identity. Активные credentials выдаются отдельно: старые авторы/регистрации остаются историческими фактами, но перенос записей не предоставляет действующие ключи, сессии или доступ.
5. Явно переключить единственное место записи. Во время cutover записи остановлены; старый endpoint/локальная копия после переноса не должны принимать конкурирующие команды. Подтверждение переноса и fencing старого писателя требуют отдельного согласованного контракта.
6. После сверки оставить локальную исходную копию архивом. Обратный переход в автономный режим — такой же явный перенос с новой проверкой полномочий, а не автоматический failover при обрыве сети.

Нельзя объединять разошедшиеся журналы по времени или правилу «последний победил». [Ограничения PostgreSQL logical replication](https://www.postgresql.org/docs/current/logical-replication-restrictions.html) включают отсутствие автоматической репликации DDL/схемы и sequence state. Репликация таблиц сама не определяет правила identity, человеческих решений, локальных файлов или переноса полномочий; её не выбираем как готовый протокол продукта.

## Устройства, файлы и исполнение

По умолчанию не загружать код, абсолютные пути, `.env`, ключи, cookies, пароли и настройки других приложений. Содержание evidence, отчётов и текста проекта тоже может быть чувствительным; оно входит в видимое согласование состава публикации. Шифрование транспорта/диска не означает сквозное шифрование: сервер обрабатывает разрешённые данные в открытом виде.

Будущий device bridge устанавливает только исходящее защищённое соединение. При pairing человек выбирает конкретные account/project/device и локальную папку; отдельный отзываемый ключ ограничен возможностями. Cloud не присылает произвольный абсолютный путь, URL, shell, argv или env. Право читать заданные относительные файлы отделено от права запуска.

Локальные пути/identity папки остаются device-local; смена папки требует явного переподключения. File reads наследуют anchored-path, secret-name, symlink/hardlink и size guards из [workspace-files](../../lib/workspace-files.ts), дополняются allowlist и видимым разрешением передачи. Эти ограничения не доказывают отсутствие всех секретов в разрешённом файле.

Доверенный запуск требует отдельной изолированной среды без host credentials, production DB, Docker socket и доступа к чужим проектам; лимиты CPU/RAM/диска/времени, контролируемая сеть, временные outputs и проверяемый provenance результата. Повтор после потери ответа не должен повторно запускать процесс до установления исхода первого запуска. Исходные входы/хеши и факт реального места выполнения сохраняются; отчёт устройства не переименовывается в доказательство серверного процесса.

## Доступ, хранение и восстановление

- Пароли, raw session/reset/invite tokens и private keys не реплицируются. Устройства и агенты имеют отдельные полномочия, ротацию и отзыв. Cloud login не превращает локальный кэш в local-owner обход проверок membership.
- Отзыв блокирует последующие запросы и подписки; уже скачанные байты невозможно гарантированно стереть с отключённого устройства. Для кэша нужны настройки хранения, шифрование ключом ОС и очистка после logout/revoke с честным описанием этого ограничения.
- Для облака отдельно определить доступ операторов, регион хранения, сроки хранения истории/артефактов/логов/backups и удаление аккаунта/проекта. Append-only журнал не заменяет согласованную политику удаления и минимизации персональных данных.
- Backup зашифрован, имеет ограниченные права и копию вне основного сервера; восстановление проверяется на отдельной базе. Секреты и сертификаты требуют своего защищённого восстановления. RPO/RTO выбираются до обещаний пользователям.
- Миграции и обновление протокола проверяются на копии; приложение отказывается писать с несовместимой схемой. После новых записей нельзя откатывать старый backup поверх работающей базы. Требуются сохранение новых фактов, план восстановления и отдельная сверка.

## Этапы приёмки

| Этап | Что должно быть доказано до заявления готовности |
| --- | --- |
| A. Интеграция | `feature → dev → main`, актуальные проверки общего дерева UI/verification, 010/011 migration/reopen и сохранность прежних событий/receipts; точные SHA и версия протокола |
| B. Online hosting | Настоящий TLS `ouroapp.ru`, один service process, demo off; реальная PostgreSQL и restore drill; login/invite/reset/SMTP; два аккаунта и проекта без cross-scope чтения/записи/SSE/MCP; отсутствующие локальные capabilities видимы |
| C. Управляемая публикация | Выбран один проект; сохранены IDs/хеши/авторы/receipts и verification provenance; перенос не выдаёт старые credentials; остановка записей, конфликт ID и сбой cutover не дают двух писателей |
| D. Кэш и offline drafts | Перезапуск сохраняет pending/unknown и точный retry; late response/revoke/CAS/schema gap не принимают неверные решения; Yjs converges, опубликованный draft сохраняет несогласованные изменения для явного нового черновика |
| E. Device bridge/runner | Pairing/revoke, path escape/secret/scope guards, обрыв связи и повтор запуска; изоляция ОС/сети/ресурсов; provenance не повышается от текста отчёта и чужой GREEN не принимается |

## Решения и оставшиеся уточнения

1. **Согласовано 03.11.2026:** автономные local-проекты и online cloud-проекты с единственным журналом; кэш чтения и offline-черновики — следующий этап. Это не разрешение автоматически переносить существующие проекты.
2. Первый hosted-запуск — новый приватный проект по приглашениям или управляемый перенос конкретного существующего проекта? Какие данные разрешено передать?
3. Где размещать PostgreSQL/backups, кто имеет операторский доступ и какие требуются сроки хранения, RPO/RTO?
4. Для verification достаточно локальных агентов/импортированных отчётов в первом облачном выпуске или нужен отдельный пакет device bridge и изолированного runner до начала использования?

Доступность домена разрешает продолжить подготовку сервиса. Она сама не означает согласование переноса рабочих данных, новых правил синхронизации или удалённого исполнения кода.
