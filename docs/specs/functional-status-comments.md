База рабочего среза со скриншота: `918aadd`; изолированная ветка `codex/functional-status-comments`. Текущие рабочие каталоги и пользовательские БД не изменяются.

## Обязательная последовательность

1. Детерминированные проекции статусов и доступности действий; согласованный scope спеки, ревизии и попытки. Затем отображение реальных процессов и событий.
2. Навигация проекта и формы в пределах комментариев.
3. Визуальное оформление поверх действующего стека React, Next.js, React Flow, Dagre, Lucide и CSS. По последующему прямому запросу пользователя общий выбор переведён на Base UI1.9; библиотечное поведение имеет приоритет перед статичной Figma.

## Сохранение контрактов

- Канонические lifecycle-значения не мигрируют ради оформления; uppercase — только показ кода.
- `succeeded` не означает `done`; приёмка требует человеческого evidence каждого обязательного DoD и серверных guards.
- Действующий домен намеренно допускает resume/ACK до отдельного подтверждения применения положительного решения; завершение строгого шага имеет собственные guards. UI не вводит дополнительный запрет скрытно.
- Исторические ревизии доступны только для чтения. Старая primary не становится статусом новой активной ревизии.
- При проверке доступности используется чистый command guard probe, без сохранения событий; полномочия на запись повторно проверяет сервер.
- Неизвестный исход команды сохраняет исходные project/actor/requestId/body. Повтор создаёт тот же запрос, а не новую команду.
- Тип клиента старых регистраций неизвестен; бренд не выводится из имени. Поле client metadata и миграция не добавляются ради иконки.
- Абсолютный путь к ключу вводится вручную. Browser file input не обещает абсолютного пути и не читает/отправляет секрет ради выбора файла.
- Производственные данные, реальные ключи, права доступа, релизы и развёртывание не входят в пакет.

Остаточные критерии №13, 17, 19, 21 и 22 уточнены в [отдельном пакете](review-followups.md). Изменения статусной модели и контрактов описаны [для согласования](../proposals/status-contract-followups.md) и не включаются автоматически в UI-правки.

Регрессии на согласованные graph/list статусы, новую ревизию после старого результата, resume/apply/ACK, scope ревизии/попытки, Reality без Flow и без выдуманной причинности, формы/диалоги и UNKNOWN. Затем typecheck, затронутые browser-сценарии, production build и визуальная проверка реального интерфейса. Результаты и ограничения фиксируются отдельно после выполнения.
