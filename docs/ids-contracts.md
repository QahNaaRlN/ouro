# Ouro: идентификаторы, контракты и границы интеграции

Статус: контракт требований и проектные модели, сопоставленные с ограниченным прототипом `0.1.0-alpha.12`; состояние актуализировано 29.10.2026. [Текущие пакеты](roadmap.md), [проверки](validation.md), [физическое хранение](implementation.md). API не объявлено стабильным production-контрактом. Исходная дата документа: 2026-10-28.

Разделы 3–6 и предлагаемый формат ошибок ниже сохраняют целевую семантическую схему; их псевдокод и имена полей не заменяют текущий wire-контракт. Нормативный источник формата версии `0.1.0` — [каталог `@ouro/protocol`](../packages/protocol/schemas/manifest.json) и его JSON Schema. `tools/list` публикует inputs и outputs 15 инструментов, включая четыре исходных report-инструмента; MCP resources предоставляют manifest/bundle через HTTP и stdio. При расхождении формата с псевдокодом используется объявленная схема соответствующей версии. [Установка и совместимость](protocol-guide.md).

В standalone-прототипе `expectedVersion` относится к единому проектному потоку, все агентские отчёты относятся к назначенному `executionId`, а project/spec/revision выводятся сервером из назначения. У Action фазы `started/completed/failed`, evidence — строка; варианты имеют `{id,title,description}`. Output schema включает `ok:true` и `ok:false`; error `isError:true` не исключает проверку structuredContent клиентом. Конверт события описан, payload/error details остаются JSON-расширениями. [Использование](agent-quickstart.md).

Зафиксированные требования пользователя: Human View предназначен для человека; Question требует участия человека; должны быть разработаны раздельные статусные модели, именование спек, неизменяемая история и согласованные контракты; проект использует SemVer; в дальнейшем Ouro интегрируется в Meridian.

## 1. Методология идентификаторов

Рабочая трактовка: **Human ID** и **Agent ID** — два представления идентичности одной спеки. Это предположение для проекта методологии; пользователь ещё не уточнял, имел ли он в виду идентификаторы авторов. Поэтому идентификаторы участников определены отдельно.

| Назначение | Поле | Формат и пример | Правило |
|---|---|---|---|
| Машинная идентичность спеки, Agent ID | `spec.id` | UUID, например `9c1444cf-3b88-4f66-a6ea-327647b96857` | Глобально уникален, неизменен, выдаётся сервером. Канонический FK; в параметрах MCP/API называется `specId`. |
| Читаемый ключ спеки, Human ID | `spec.humanId` | `<PROJECT>-S-<NNNNNN>`, например `OURO-S-000123` | Уникален в пространстве проекта; закреплён навсегда, не переиспользуется после архивации. |
| Номер ревизии для человека | `revision` | Целое `1`, `2`, `3` | Возрастает внутри спеки, не меняет её идентичность. |
| Машинная идентичность ревизии | `specRevisionId` | UUID снимка содержания | Для исполнения и команд фиксируется именно эта неизменяемая ревизия. |
| Номер версии агрегата | `expectedVersion` | Неотрицательное целое | Защита команды от записи поверх более нового состояния, не версия текста спеки. |
| Человек-участник | `actor.principalId`, `actor.kind=human` | Стабильный ID в реестре участников | Отдельная сущность от Human ID спеки; отображаемое имя можно изменить. |
| Агент-участник | `actor.principalId`, `actor.kind=agent` | Стабильный ID в реестре участников | Отдельная сущность от Agent ID спеки; конкретная сессия агента имеет `agentInstanceId`, исполнение задачи — `executionId`. |

Для предотвращения путаницы поле `agentId` **не используется как ID спеки**. В API используется `specId`; термин Agent ID допускается в пояснениях к методологии как машинный идентификатор спеки.

В читаемых ключах префикс сущности отделяет тип: `S` — Spec, `R` — Roadmap, `X` — Execution, `D` — DecisionRequest, `E` — Reality Event. Для MVP читаемый ключ обязателен только для спеки; остальные сущности могут отображать короткую производную своего UUID, если полный реестр Human ID для них не нужен. Эта сокращённая подпись не становится каноническим идентификатором API.

Проектный код (`OURO`) резервируется внутри workspace и не меняется автоматически вслед за названием проекта. Полный человекочитаемый адрес включает workspace/project, если короткий ключ используется вне текущего проекта. Сервер разрешает `humanId` в `specId` только в заданном project scope. Межпроектный поиск не выбирает случайное совпадение.

Последовательность Human ID выдаёт сервер в транзакции. Пропуски номеров допустимы; сортировка, приоритет и порядок исполнения не выводятся из номера. Перенос в Meridian сохраняет `specId`, исходный `humanId` и отдельное соответствие внешнему ID.

### Название и отображение

Заголовок формулирует результат и объект: «Сохранять решение человека по развилке», «Восстанавливать историю спеки после переподключения». Желательный размер — 4–12 слов; это редакционная рекомендация, а не блокирующее ограничение.

Не включать в название статус, ответственного, спринт, дату или номер версии. Идентификатор и статус отображаются отдельно: `OURO-S-000123 · Сохранять решение человека по развилке · r3 · В работе`.

Переименование создаёт новую ревизию, но сохраняет оба идентификатора. Новая ревизия описывает ту же цель после уточнения; новая спека нужна для самостоятельного результата, отдельной ветви работ или замены исходной цели. Связи `derived_from`/`replaces` сохраняют происхождение. Fork сам по себе не создаёт новую спеку автоматически.

## 2. Версии

| Что версионируется | Политика |
|---|---|
| Продукт Ouro | `MAJOR.MINOR.PATCH` по SemVer; текущая предварительная сборка — `0.1.0-alpha.12`, первый исторический срез — `0.1.0-alpha.1`. Production-релиз не выполнен. |
| `@ouro/core`, `@ouro/mcp`, `@ouro/view` | На раннем этапе единая версия релиза для совместимого набора. Пакеты публикуются только когда существует реальный потребитель и процесс публикации. |
| `@ouro/protocol` | Самостоятельный контракт `0.1.0`, независимый от продукта и MCP transport. Поддерживается точная объявленная версия; установка `.tgz` проверена, публикация в npm registry не выполнялась. |
| Схемы событий и команд | `schemaVersion:1` событий сохраняется отдельно. На линии 1.x слом полей/семантики/прав требует MAJOR; для текущей 0.x действует описанная ниже локальная политика. Старые события и receipts не переписываются под новую версию пакета. |
| Содержимое спеки | Неизменяемые последовательные ревизии `r1`, `r2` и т. д.; SemVer не применяется к каждому редактированию задачи. |
| ТЗ и ТС | Явные версии документов и журнал изменений; номер документа не подтверждает выпуск приложения. |

Для стабильной линии 1.x: patch — совместимое исправление; minor — совместимое расширение; major — несовместимость объявленного публичного API. В линии 0.x предлагается локальное правило Ouro: несовместимость повышает MINOR, совместимое изменение повышает PATCH; изменения документируются и координируются с интеграцией Meridian. Это более строгая политика проекта, а не дополнительное требование стандарта SemVer. Опубликованная версия не перезаписывается. Pre-release не обозначает готовность к production.

Добавленное необязательное поле может быть совместимым, а новый enum-вариант способен сломать строгого потребителя. Правила совместимости должны учитывать фактические декодеры, а не только наличие старых полей. Потребитель не исполняет неизвестную команду или семантически неизвестное событие; адаптер явно сообщает несовместимость.

## 3. Общий конверт команды и события

Целевая общая семантика четырёх исходных отчётных MCP-инструментов:

```ts
type CommandContext = {
  requestId: string;        // UUID, ключ идемпотентности
  projectId: string;
  specId: string;           // Agent ID спеки
  specRevisionId: string;    // ревизия, относительно которой агент работал
  executionId?: string;   // для Action/Fork/Blocker обязателен; Question может быть на уровне спеки
  expectedVersion: number; // версия execution при наличии executionId, иначе spec
};
```

Principal отправителя, его project scope и полномочия определяются аутентифицированным транспортом. Переданное агентом имя автора не является доказательством личности. Разрешение читателей Human View и отправителей MCP проверяется сервером.

Серверный конверт принятого доменного события содержит `eventId`, `eventType`, `schemaVersion`, `workspaceId`, `projectId`, `specId`, `specRevisionId`, `executionId?`, `aggregateType`, `aggregateId`, `aggregateVersion`, `actor`, `occurredAt?`, `recordedAt`, `correlationId`, `causationId?`, `requestId`, `payload`. `actor` содержит `kind`, `principalId`, необязательный `agentInstanceId`. Workspace и actor устанавливаются сервером. Состояние approval не записывается поверх исходного события.

`aggregateVersion` задаёт порядок внутри одного агрегата. Клиентское время можно сохранить как диагностическое поле, но порядок и авторитет решения не выводятся из него. Подписка использует серверный cursor и умеет воспроизводить пропущенные события после разрыва. Cursor нельзя подменять timestamp с возможными совпадениями.

Идемпотентность проверяется по `(principalId, projectId, commandType, requestId)`: повтор того же тела возвращает прежний результат; тот же ключ с иным содержимым возвращает конфликт. `hash(reason)` используется лишь как подсказка о похожем сообщении: одинаковый текст не доказывает одинаковое событие.

## 4. Четыре исходных отчётных MCP-инструмента

Вместо глобального правила «у любого события есть reason и две альтернативы» используется discriminated union отдельных схем. Все строки проверяются после trim; размеры payload и коллекций ограничиваются сервером. Порог `reason >= 50` сохраняется для Fork и Blocker как правило исходной спецификации. Сам по себе размер текста не доказывает качество объяснения.

| Инструмент | Обязательные специфичные поля | Результат и полномочия |
|---|---|---|
| `ouro.report_action` | `actionId` (UUID одного действия), `summary`, `phase: started/progress/completed`, `evidence[]` при утверждении о завершённом действии | Добавляет факт о действии. `completed` относится к действию, не утверждает завершение спеки или успешность всего исполнения. Не создаёт фиктивного approval. |
| `ouro.report_question` | `question`, `context`; `blockingScope: execution | none`; необязательные `suggestedAnswers[]`, `answerFormat` | Создаёт `DecisionRequest(kind=question, state=pending)`. Ответ человека обязателен; confidence не отменяет это требование. |
| `ouro.report_fork` | `trigger`, `context`, `reason >= 50`, `options >= 2` с уникальными `optionId`, `recommendedOptionId` | Создаёт обязательное человеческое решение. Рекомендация должна ссылаться на существующий вариант; у вариантов есть описание, последствия и компромиссы. |
| `ouro.report_blocker` | `blockerType`, `expected`, `actual`, `reason >= 50`, `impact`, `proposedPaths[]` | Создаёт блокер и обязательное человеческое решение. Если предложить путь нельзя, разрешён пустой массив с обязательным `noPathReason`; выдуманные альтернативы не требуются. |

`actionId` связывает все сообщения об одном действии внутри исполнения; разные команды фаз имеют разные `requestId`. При повторении работы после завершённого действия создаётся новый `actionId` со ссылкой на предыдущее. Ретроспективное сообщение о завершении допускается без ранее присланной фазы started, но остаётся одним фактом с evidence, а не восстановленной догадкой о промежуточных шагах. Пути Blocker имеют стабильный `optionId`, чтобы человек мог однозначно выбрать план; пустой список требует уточнения или добавления плана человеком до approve.

Fork и Blocker останавливают зависимое исполнение в `waiting_for_human`. Question указывает `blockingScope: execution | none`: неблокирующий вопрос остаётся обязательным для ответа человека, но не останавливает независимую работу. Если остановка касается части работ, эта часть выделяется собственным `executionId`; сервер не разрешает ослабить уже действующую блокировку. Таймаут ответа порождает напоминание или эскалацию; он не считается согласием.

Принятие команды означает сохранение события, а не одобрение предложения. Ответ:

```ts
type ReportResult = {
  eventId: string;
  aggregateVersion: number;
  decisionRequestId: string | null;
  executionState:
    | "queued" | "running" | "waiting_for_human" | "paused"
    | "succeeded" | "failed" | "cancelled" | "skipped" | null;
  replayCursor: string;
};
```

Отдельная ось `DecisionRequest.state` принимает `pending | resolved | withdrawn | superseded`; только `resolved` имеет outcome `answered | approved | rejected`. Для Action `decisionRequestId=null`, поэтому он не получает искусственное решение. Отсрочка добавляет `DecisionDeferred` и оставляет запрос pending.

`success/fail` — системные события проверенного результата исполнения. В первой версии симулятор может порождать их с явной пометкой simulation. Четыре MCP-инструмента не дают агенту право самостоятельно удовлетворить DoD, изменить спеку или снять человеческий запрос.

Правило исходной ТС «max 10 pending per spec per agent» относится к открытым запросам решений, а не к Action. Проверка должна быть атомарной; повтор по тому же requestId не расходует лимит повторно. При превышении сервер возвращает ошибку и ссылки на существующие запросы, а не молча теряет сообщение. Агент локально останавливает затронутую работу даже при отказе публикации: ошибка inbox не является разрешением продолжить. Автоматическое ограничение не должно скрывать уже зафиксированный критический блокер; для него UI показывает необходимость человеческого вмешательства.

LLM-judge может подсказывать неполноту причины, но не заменяет схему, права или ответ человека. Для MVP он не является необходимым внешним сервисом и не должен требовать секрет ради базового сценария.

## 5. API Human View

Предлагаемая замена слишком общего `approveEvent` — типизированная человеческая команда `ouro.resolveDecision`. Разрешение запроса и управление исполнением остаются отдельными доменными действиями; UI может предложить их одной формой с явным выбором.

```ts
type ResolveDecision = {
  requestId: string;
  decisionRequestId: string;
  expectedVersion: number;
  specRevisionId: string;   // человек видел и разрешил запрос именно для этой ревизии
  outcome:
    | { kind: "answer"; answer: string }
    | { kind: "approve"; chosenOptionId: string }
    | { kind: "reject"; reason: string };
  comment?: string;
};
```

Для Question допустим ответ или мотивированное отклонение. Для Fork approve требует актуальный `chosenOptionId`. Для Blocker approve выбирает предложенный план снятия; это ещё не доказательство снятия блокера. Изменённый человеком вариант оформляется как отдельный вариант с происхождением и затем выбирается явно. Эти комбинации валидируются по `DecisionRequest.kind`. Ответ на запрос старой ревизии не переносится автоматически на новую активную ревизию.

Отдельные команды: `createSpec`, `proposeSpecRevision`, `activateSpecRevision`, `acceptSpec`, `changeSpecLifecycle`, `resumeExecution`, `cancelExecution`, `authorizeRemediation`, `deferDecision`. Агент может предлагать ревизию через ограниченный маршрут, человек её активирует. Human View показывает сравнение активной и предложенной ревизий. Наличие некоторых действий в системе не означает, что они включаются в четыре стартовых MCP-инструмента.

Решение и внешнее применение остаются раздельными. `authorizeRemediation` создаёт ограниченную попытку `executionKind=remediation` с `remediatesBlockerId`, выбранным plan/option ID и человеческим разрешением. Целевой открытый блокер не запрещает эту попытку, но сохраняет остановку основной работы; прочие блокировки действуют. Новая ревизия/инвалидация запрещает новые обычные запуски на старом контракте и инициирует остановку текущих; сохранённые исполнения и их поздние события остаются привязанными к старому `specRevisionId`.

`resumeExecution` проверяет разрешённость всех применимых запросов, наличие активной ревизии, актуальность версии и право человека. Одобрение не гарантирует существование работающего агента. Восстановление связи и подтверждение получения решения показываются отдельно.

`getRoadmap(projectId, filters)` возвращает узлы и типизированные связи с cursor/version представления. `getSpecDetail(specId, revision?)` возвращает активное ожидание, выбранную ревизию, хронологию фактов, исполнения и запросы решений. `subscribeToSpec(specId, afterCursor)` выдаёт события и служебный сигнал разрыва/replay; интерфейс после переподключения сверяет восстановленное состояние.

Конфликт двух ответов человека разрешается optimistic concurrency: принимается один ответ на ожидаемую версию, второй получает конфликт с актуальным состоянием. Исправление ответа — новое событие и при необходимости новый запрос, исходный ответ не редактируется.

## 6. Минимальная модель хранения

Ниже — концептуальные сущности для проектирования хранения, а не буквальный перечень созданных таблиц. Реальный SQL DDL 001–005 и проверенная транзакционная модель перечислены в [implementation.md](implementation.md); часть сущностей восстанавливается из доменных событий.

| Сущность | Содержание |
|---|---|
| `workspaces`, `projects` | Scope доступа и принадлежность данных; проектный код и namespace Human ID. |
| `principals` и регистрационные события | Устойчивые human/agent/service identity; отображаемые имена и внешние bindings. |
| `specs` | Неизменяемая идентичность `specId`, `projectId`, `humanId`, автор и время создания. |
| `spec_revisions` | Полный неизменяемый снимок: title, goal, DoD с устойчивыми criterionId, inputs, constraints, assumptions, risks, comment; revision, parentRevision, author, content hash. |
| `roadmaps` и события членства | Сам roadmap, принадлежность и порядок представления; lifecycle фиксируется событиями. |
| `domain_events` | Источник истины: типизированные события всех агрегатов с версиями и causation/correlation. |
| События связей | Создание/отзыв `depends_on`, `derived_from`, `replaces`, `relates_to` с типом и автором. Зависимости и происхождение имеют разную семантику. |
| События исполнений | Постановка, запуск, ожидание человека, пауза, возобновление, результат; обязательная ссылка на ревизию спеки. |
| События запросов решений | Создание Question/Fork/Blocker, отсрочка, ответ/одобрение/отклонение, отзыв или замещение запроса. |
| `command_receipts` | Неизменяемые результаты идемпотентных команд и hash принятого тела. |
| Проекции текущего состояния | Текущие состояния спек, исполнений, решений, активные связи и список уроков для чтения Human View. Восстанавливаются из domain events. |
| `integration_refs` | Явное соответствие Ouro ↔ Meridian без замены внутренней идентичности внешней. |

Слова «только INSERT» относятся к авторитетным бизнес-фактам и ревизиям. Проекции — производные: их допускается обновлять и перестраивать; это явно отделяется схемой и правами БД. Если требуется физический INSERT-only для всех бизнес-таблиц, можно сохранять версии проекций и читать последнюю, но MVP не должен платить эту сложность без отдельного требования. Технические lease/checkpoint/last_seen не представляют историческую истину о работе и имеют отдельную политику хранения.

Принятие команды, проверка expectedVersion, запись доменных событий и receipt выполняются в одной транзакции. Realtime доставляет только подтверждённые события. Сбой публикации после commit устраняется replay либо transactional outbox; Redis Pub/Sub не является хранилищем истории. Подписчик допускает повторную доставку и дедуплицирует по eventId; обещание exactly-once доставки по сети не даётся.

## 7. Граница Meridian

Ouro остаётся предметным модулем: спецификации, исполнения, события и человеческие решения. Интеграционный адаптер связывает identity/project context, маршруты UI, подписки и внешние ссылки с Meridian. `@ouro/core` не зависит от оболочки Meridian или конкретного дизайн-инструмента.

Контракты экспорта/импорта сохраняют `specId`, Human ID, происхождение ревизий, историю решений, версии схем и namespace исходной системы. UUID предотвращает конфликт машинной идентичности; проектный namespace предотвращает неоднозначность коротких ключей. Адаптер не переписывает старые события, чтобы подогнать их под внешний формат.

Визуальная основа сверена с доступными Figma-макетами и variables/styles: [источник и границы проверки](design-reference.md). Ouro-side адаптер использует закреплённые статические light/dark tokens; это не подписка на нативную тему Meridian. Старые предложения палитры Ouro не подменяют фактический источник.

Изучены реальные desktop DTO, provider/workspace/project и run/spec/context pins, native IPC/CSP/capability и палитра Meridian. [Импорт](meridian-guide.md) сохраняет provenance без утверждения подлинности. Способ нативного встраивания, credential provisioning, SSO/tenancy и Windows-приёмка остаются отдельным пакетом по [конкретному RFC](proposals/meridian-native-bridge.md); live host интеграция не заявляется.

## 8. Критерии согласованности контрактов

1. Повтор одной команды не создаёт второй факт или второй запрос человеку.
2. Разные сообщения с одинаковой причиной не исчезают из-за hash(reason).
3. Агент не может присвоить себе human identity, ответить на свой Question или активировать собственное изменение ожидания.
4. Ответ по устаревшему состоянию возвращает конфликт, а не перезаписывает более новое решение.
5. Завершение Action не переводит автоматически спеку в done.
6. Approve Blocker не закрывает блокер без проверяемого факта снятия.
7. Переименование, новая ревизия и импорт в Meridian сохраняют машинную идентичность.
8. Human View после replay показывает то же состояние и основания решений, что и до разрыва соединения.

## 9. Общие ошибки команд

Для текущего wire-контракта используйте `agentErrorSchema` и output schema выбранного tool из [каталога версии 0.1.0](../packages/protocol/schemas/manifest.json): тело имеет форму `{ok:false,error:{code,message,details?,retryable,refreshRequired}}`. Следующий предложенный формат и таблица сохраняют проектный контекст; они не являются заменой исполняемой схемы. `OUTPUT_CONTRACT_ERROR` с `error.details.outcomeUnknown:true` не доказывает отсутствия commit: сохраните requestId и полное тело для точного повтора. Отказ доступа после потерянного ответа также не является proof-of-absence.

Предлагаемый формат: `{code, message, requestId, retryable, details?}`. `details` может включать актуальную версию и ссылку на разрешённую пользователю сущность; ошибки не раскрывают данные другого проекта.

| code | Условие |
|---|---|
| `UNAUTHENTICATED` / `FORBIDDEN` | Не установлена личность либо отсутствует право на команду/проект. |
| `NOT_FOUND` | Сущность не найдена в разрешённом scope. |
| `VALIDATION_ERROR` | Поля, комбинация outcome или option ID не соответствуют схеме запроса. |
| `VERSION_CONFLICT` / `REVISION_CONFLICT` | Изменился агрегат или команда относится к другой активной ревизии. |
| `DECISION_ALREADY_RESOLVED` | Уже принято несовместимое решение; идемпотентный повтор исходной команды возвращает прежний результат. |
| `INVALID_TRANSITION` | Запрещён переход состояния либо продолжение при неснятой блокировке. |
| `PENDING_LIMIT_EXCEEDED` | Достигнут лимит открытых запросов; новый запрос не был сохранён. |
| `IDEMPOTENCY_CONFLICT` | Один requestId повторно использован с другим телом. |

`REVISION_CONFLICT` запрещает новые запуски, изменение ожидания и применение решений к устаревшему контексту. Он не должен терять аутентифицированный поздний отчёт о факте уже существующего execution старой ревизии: такой отчёт принимается в исторический контекст, не возобновляет работу и не подтверждает DoD текущей ревизии. Терминальное состояние исполнения не переписывается поздним отчётом.

Прототип реализует runtime-валидацию домена, HTTP, настоящих MCP HTTP/stdio и выделенного Meridian импорта. Flow и input/output схемы получаются из `@ouro/protocol`; canonical bundle содержит 34 схемы Draft 2020-12, а закреплённый MCP SDK публикует wire Draft 7. Каталог версии и общие определения являются источником формата, этот псевдокод — объяснением проектной семантики. tRPC transport, полный типизированный каталог event payload и пакетные roadmap proposals не реализованы. Клиент сохраняет requestId/тело при неизвестном исходе и не пересылает конфликтующую команду с новой версией без чтения состояния и явного решения. [Подключение](agent-quickstart.md), [инструкция контракта](protocol-guide.md), [текущие границы](roadmap.md).
