# Реализация прототипа и границы проверки

## Текущий срез `0.1.0-alpha.15`

Подключение Cursor, Claude Code и Claude Desktop использует прежний stdio bridge и общий MCP-контракт `0.1.2`, без новых tools, доменных статусов, миграций или отдельных клиентских серверов. В дашборде выбирается профиль клиента; pure `buildAgentClientConfig` формирует entry и wrapper `mcpServers`, а CLI `npm run --silent agent:config -- …` печатает тот же JSON. Ключ остаётся в отдельном файле, конфигурация содержит только его абсолютный путь. Полный projectId в имени сервера предотвращает замену соседнего подключения с одинаковым коротким префиксом.

Конфигурация доступна независимо от показа одноразового ключа, проверяется при смене пути/клиента/проекта и может копироваться либо скачиваться. Программа не редактирует существующие настройки Cursor/Claude и не запускает модель. Проектный URL, actor, server authority и queued/ACK правила сохраняются. Локальный stdio не требует туннеля ChatGPT. [Инструкция клиентов](agent-clients-guide.md), [SDD](specs/client-onboarding.md), [журнал приёмки](plans/client-onboarding.md).

## Основа: срез `0.1.0-alpha.14`

Новый вход `/projects` связывает каталог папок локального оператора с отдельными историями проектов. Проект открывается в живом дашборде: дорожная карта, процесс выбранной спеки, попытки/агенты, требующие решения события и лента фактов используют один scoped snapshot. Назначение создаёт спеку, активную ревизию и queued-попытку атомарно; running появляется только по агентскому ACK. Подтверждённые MCP-события попадают в SQL и затем в scoped SSE, а не рисуются предположительно по клику человека. [Спецификация](specs/project-workspace.md), [пользовательская инструкция](project-workspace-guide.md), [SDD/TDD](plans/project-workspace.md).

Сервер владеет одним SQL/PGlite connection и общей очередью записи. Cached facades `store.forProject(id)` замыкают явный projectId, делят owner и не открывают PGlite повторно. Миграция [006_workspace_projects.sql](../db/migrations/006_workspace_projects.sql) добавляет каталог папок/неизменяемых root bindings и receipts создания. `ProjectInitialized` задаёт собственную дорожную карту через replay; новые папки не получают учебных спек. Старые события, хеши и receipts не переписываются. Реестры participants/drafts и GitHub lease sweep также ограничены project scope.

HTTP `/api/projects/{id}/…` и MCP `/api/projects/{id}/mcp` фиксируют один проект. UI не хранит авторитетную «текущую папку» в cookie; переключение экрана не меняет контекст подключённого агента. Доступ к каталогу предоставлен только доверенному локальному оператору; полноценная multi-user tenancy не реализована. Unknown intent хранит исходные URL/project/actor/request/body и повторяется туда же после внутренней навигации. Долговременного восстановления intent после закрытия вкладки нет.

Общий контракт `@ouro/protocol@0.1.2` содержит 18 MCP tools и 49 canonical схем. Два новых read-only tools дают назначенному агенту ограниченный файловый контекст: пагинированный список и UTF-8 файл с SHA-256. Абсолютный root остаётся на сервере; assignment проверяется до IO. Root identity, containment, symlink/nonregular/hardlink/credential/binary/size guards описаны в [SDD](specs/project-workspace.md). Сервер не пишет в выбранную папку и не запускает там команды. ChatGPT — пример клиента общего MCP-контракта; собственных доменных статусов ChatGPT нет. Настоящая настройка аккаунта/туннеля отдельно описана в [инструкции](chatgpt-guide.md), её не заменяет тест SDK.

## Предыдущий срез `0.1.0-alpha.13`

Исполняемый domain/store отделён от HTTP/MCP и интерфейса. [Дорожная карта](roadmap.md) и [валидация](validation.md) связывают текущие функции с SDD/TDD; далее сохранены датированные описания ранних срезов.

`packages/protocol` выделен в самостоятельный `@ouro/protocol@0.1.1`. Полный Flow и enforced-профиль, runtime/step/traversal/view, входы 16 tools, DTO ответов и ошибок, manifest и 41 canonical JSON Schema имеют общий источник. Пакет собирается в ESM/CommonJS с соответствующими declarations, JSON-файлами, примерами и CLI. Runtime зависит только от Zod; ни Next.js, ни store, ни MCP SDK в него не входят. Корневое приложение использует тот же публичный скомпилированный пакет через file-зависимость и npm build hooks. Текущая ветка — `feat/flow-runtime`. [Каталог](../packages/protocol/schemas/manifest.json), [отдельная установка](../packages/protocol/README.md), [интеграционная инструкция](protocol-guide.md).

HTTP и stdio публикуют статические resources `ouro://protocol/manifest` и `ouro://protocol/schemas`; к прежним 15 tools добавлен `ouro.report_flow_step`. Canonical dialect — Draft 2020-12, wire-экспорт закреплённого SDK — Draft 7. Output схемы описывают обе ветви `ok`; `validateToolBody` сохраняет исходные дополнительные JSON-поля, а inputs/Flow закрыты. Конверт события описан, payload и error details остаются JSON-расширениями. Самостоятельный JSON-валидатор не заменяет графовые, lifecycle, authority и idempotency guards приложения.

Ошибки сериализации/проверки ответа после commit дают безопасный неизвестный исход с требованием сохранить requestId/body/expectedVersion. Квитанции и legacy optional-поля остаются совместимыми без перезаписи SQL-истории. Исходный пакет контракта alpha.12 сохранён в своём [журнале SDD/RED/GREEN](plans/domain-contract.md).

Alpha.13 добавляет отдельную ось **FlowStepRun** только при новом человеческом `startExecution` с `flowTracking:'enforced'`. ExecutionCreated содержит ready-run входа, дальнейшие события воспроизводят Execution.flowRuntime с visits, evidence и traversals. Один текущий проход задаёт исключающий маршрут; слияние входов не синхронизирует параллельные ветви. Complete и следующий ready-run с traversal записываются одной командой, retry создаёт новый run, skip разрешён человеком только для ready action/wait с одним исходом. Result завершает маршрут отдельно от итога execution и приёмки DoD. Новая SQL-миграция не добавлена, старая история не дополняется предполагаемыми проходами.

Новые отчёты строгой попытки требуют flowStepRunId; поздний actionId сохраняет исходный run. Внеплановый Question/Fork/Blocker получает серверную связь flowInterrupt без изменения immutable Flow. Человеческие решение, применение/устранение, resume и ACK проверяются отдельно. `buildFlowRuntimeView` использует то же доменное ядро для agent/human actions и пяти edge states; UI хранит явно выбранный прежний run при SSE. Учебный симулятор пишет только явно синтетические `simulation://` evidence своего назначения. [Инструкция и ограничения](flow-runtime-guide.md), [SDD/RED/GREEN и текущий gate](plans/flow-runtime.md).

|---|---|

| [002_agents.sql](../db/migrations/002_agents.sql) | Отдельные регистрации/хеши ключей/отзывы агентов и техническая presence-проекция |

Авторитетная бизнес-история остаётся append-only. Техническая presence, lease, SQL-head черновика и проектный cursor имеют отдельную политику обновления. Yjs updates не меняют domain cursor; публикация атомарно создаёт новую immutable ревизию и закрывает технический черновик, а активация остаётся отдельной человеческой командой. Human revocation повторно проверяется под project lock перед записью. [Участники](participants-guide.md), [черновики](collaboration-guide.md), [GitHub](github-guide.md).

Сводки/предложения внешнего MCP-агента, уроки и происхождение новых idea-спек хранятся доменными событиями, без отдельной новой миграции. Meridian импорт проходит выделенный серверный маршрут с повторной строгой проверкой, точным raw JSON/SHA-256 и статусом `unverified_import`; обычная команда не может выдать себя за подтверждённый импорт. [Предложения](agent-proposals-guide.md), [Meridian](meridian-guide.md).

Проверки выполнены на PGlite. Адаптер `pg` и `DATABASE_URL` предусмотрены, но внешний PostgreSQL и многопроцессное развёртывание отдельно не приняты. Один настроенный проект, ограниченные графы/документы, отсутствие production SSO/RBAC/tenancy и нативного Meridian host остаются явными границами.

## Домен и хранение

`packages/core/src` содержит независимые от Next.js типы, проверку команд, правила переходов, проверку циклов и чистое воспроизведение событий. `lib/store.ts` отвечает за транзакции, идемпотентность и долговечность. Веб-маршруты получают личность из серверного контекста, а не из поля `actor` клиентской команды.

По умолчанию используется **PGlite с PostgreSQL 17.5**, сохраняющий данные в `.ouro/postgres`. Это PostgreSQL в WebAssembly, а не имитация SQL в памяти. Путь можно изменить переменной `OURO_DATA_DIR`; каталог исключён из Git. PGlite в данном адаптере предполагает **один процесс Node.js, владеющий каталогом данных**. Глобальный объект приложения переживает обновление модулей в режиме разработки и сохраняет единственный экземпляр подключения.

Для внешнего PostgreSQL предусмотрен адаптер `pg`: задаётся `DATABASE_URL` на выделенную базу Ouro. Оба адаптера исполняют один файл [001_initial.sql](../db/migrations/001_initial.sql). Проверки в этой сессии выполнены на PGlite; подключение к внешнему серверу PostgreSQL, его резервное копирование, TLS, отдельные роли БД и многопроцессная нагрузка ещё не проверены.

Первое открытие базы транзакционно применяет миграцию и, если версия проекта равна нулю, записывает демонстрационные события. Повторное открытие существующей базы не перезаписывает историю и не добавляет seed повторно.

## Что считается источником истины

| Записи | Назначение | Изменяемость |
|---|---|---|
| `ouro_domain_events` | Полные типизированные события с автором, схемой, версией проекта и контекстом | Только INSERT |
| `ouro_spec_revisions` | Полные снимки редакций, номер и SHA-256 содержания | Только INSERT |
| `ouro_specs` | Постоянные машинные и читаемые идентификаторы | Только INSERT |
| `ouro_principals` | Устойчивое соответствие ID и типа участника | Только INSERT |
| `ouro_command_receipts` | Хеш команды и исходный результат её принятия | Только INSERT |
| `ouro_outbox` | События, готовые для доставки после commit | Только INSERT |
| `ouro_projects.version` | Технический курсор и блокировка конкурентной записи | UPDATE допустим |

На таблицы авторитетных записей установлены триггеры, запрещающие `UPDATE`, `DELETE` и `TRUNCATE`. Они предотвращают случайную перезапись обычным SQL. Владелец базы или администратор всё ещё может менять DDL; промышленная модель ролей с отдельным владельцем миграций и ограниченной прикладной ролью — отдельная задача развёртывания. HTTP-доступа к произвольному SQL нет.

Текущее состояние не хранится изменяемой бизнес-строкой: чтение воспроизводит журнал через `replay`. Это облегчает проверку соответствия истории и интерфейса. Исправление прошлого оформляется новым событием или новой ревизией; старый снимок не редактируется. При вставке ревизии повторно проверяется совпадение хеша с ранее сохранённым содержанием.

## Транзакция команды и порядок событий

Одна команда выполняется так:

1. Проверяется серверный участник и доступ к проекту, форма `requestId` и `expectedVersion`.
2. Блокируется строка проекта `SELECT … FOR UPDATE`. Во внешнем PostgreSQL это также сериализует разные процессы приложения.
3. Проверяется receipt по ключу `(projectId, actorId, requestId)` **до проверки ожидаемой версии**. Тот же JSON с другим порядком ключей распознаётся как та же команда. Иное содержимое с тем же ключом получает `IDEMPOTENCY_CONFLICT`.
4. Журнал воспроизводится; ядро проверяет версию, полномочия, активную ревизию, тип решения и допустимость перехода.
5. События, новые снимки ревизий, записи outbox, курсор проекта и receipt записываются одной транзакцией.
6. Только после commit результат возвращается клиенту. Любая ошибка, в том числе отказ записи outbox, откатывает все изменения команды.

Повтор принятой команды возвращает её **исходный** ответ и курсор с `replayed: true`; он не повторяет доменное действие. Если после исходной команды уже были другие изменения, клиент отдельно читает актуальный снимок, а не заменяет его старым receipt.

Для первой версии выбран один возрастающий курсор/номер версии на весь демонстрационный проект. Это более консервативная защита, чем независимая версия каждой спеки: параллельные изменения разных спек могут конфликтовать. Зато порядок commit и курсор согласованы, отсутствует неоднозначность восстановления пропусков. При конфликте интерфейс читает новое состояние; человеческое решение не пересылается автоматически с новой версией.

`getEvents(after)` возвращает все committed-события после курсора и текущий курсор в согласованной транзакции. Номер версии выделяется под блокировкой и не переживает rollback. Неуспешная команда не создаёт скрытого пропуска. Идентичность события и причинные ссылки отделены от времени для отображения.

Outbox уже сохраняется атомарно, однако внешний брокер, его publisher и подтверждения доставки в этой версии не реализованы. Клиент восстанавливает историю чтением по курсору. Это не обещание exactly-once сетевой доставки или физической остановки настоящего агента.

## Область идентичности и симулятор

Прототип содержит один заранее определённый проект. Проверка scope есть в ядре и хранилище, но полноценный реестр организаций, workspace и членства не реализован. Тип зарегистрированного участника нельзя поменять с `agent` на `human`, переиспользовав тот же ID.

Локальная демо-сессия разрешена только при `OURO_LOCAL_DEMO=1` и loopback-адресе. Для внешних адаптеров предусмотрены разные серверные bearer-ключи человека и агента. Это ограниченная демонстрационная граница, не готовая система аккаунтов/SSO. Не следует публиковать локальную демо-сессию через обратный прокси как промышленную авторизацию.

Симулятор демонстрирует сообщения агента и подтверждения отдельно от команд человека. Его действие не является реальным изменением репозитория или исполнением кода. Одобрение развилки не означает успех попытки; одобрение плана Blocker не снимает препятствие; успех попытки не означает принятия DoD. Правила проверяются серверным ядром, а не только доступностью кнопок.

## Проверки хранения

- `npm test`: доменные проверки и [storage.test.ts](../tests/storage.test.ts).
- `npm run db:check`: миграция реального PGlite, запрет перезаписи и сравнение состояния после закрытия и повторного открытия каталога базы.
- `npm run typecheck`: проверка TypeScript всего проекта.

Storage-тест проверяет идемпотентный повтор после последующих записей, конфликт изменённого payload, запрет чужого scope, единственного победителя двух конкурентных команд, откат события и receipt при искусственном отказе outbox, запреты `UPDATE`/`DELETE`/`TRUNCATE`, непрерывный cursor replay, повторное открытие базы и невозможность повысить агентскую идентичность до человеческой.

Для масштаба за пределами демонстрации нужны checkpoint-проекции, постраничные чтения журнала, компактные receipts и политика хранения/резервного копирования. Сейчас проект воспроизводится целиком, а receipt сохраняет полный исходный ответ. Эти решения выбраны для проверяемости небольшого прототипа, не как результат нагрузочного теста.

Обоснование архитектурных принципов и первичные источники: [исследование](methodology-research.md), [методология диаграмм](diagram-methodology.md), [статусные модели](status-methodology.md).
