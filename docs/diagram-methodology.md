# Методология дорожных карт, блок-схем и причинных диаграмм Ouro

Редакция: 2026-10-28. Применяется совместно со [статусной моделью](status-methodology.md). Обоснование и литература: [исследование первоисточников](methodology-research.md).

## 1. Сначала вопрос, затем вид диаграммы

| Вопрос человека | Представление | Разрешённые отношения | Циклы |
|---|---|---|---|
| Что нужно получить и что должно быть готово раньше? | Roadmap / граф зависимостей | Предпосылка → зависимая спека, группы этапов | Обязательные зависимости ацикличны |
| Какие пути возможны, кто выбирает и где ждать? | Flow / процесс | Действие, условие, выбор, ожидание, результат | Возможны в шаблоне процесса |
| Что произошло и на каком основании? | Reality / причинный граф и журнал | Зафиксированные события → их последствия | Ссылки идут к уже существующим причинам; повтор — новый факт |
| Что происходило раньше/позже? | Timeline событий | Номер последовательности и время | Не применимо |
| Когда планируется работа? | Календарная roadmap | Реальные start/target даты или итерации | Без дат шкала не показывается как обещанный план |

Группа этапов, позиция карточки и линия «связано с» не создают обязательную зависимость. Временная последовательность двух событий сама по себе не доказывает причинность. В интерфейсе легенда и подписи объясняют типы линий.

## 2. Рабочий протокол создания roadmap

1. Определить наблюдаемый результат этапа. Каждая спецификация получает стабильный Human ID, название с действием и проверяемый DoD; детали ожидания принадлежат конкретной ревизии.
2. Выделить только реальные предпосылки: «без результата A нельзя начать B». Для простой тематической близости использовать отдельную связь `relates_to`, которая не блокирует запуск.
3. Записать ребро **A → B**: A — предпосылка, B — зависимая спека. Для формы ввода использовать названия «Предпосылка» и «Зависимая работа», не неоднозначные «откуда/куда».
4. Проверить существование обоих концов, один проект, отсутствие self-loop и дубликата. Перед добавлением A → B проверить, существует ли путь B → A; если да, показать найденную цепочку и отказать атомарно.
5. Сохранить предметное изменение событием с автором и причиной. Запуск проверяет удовлетворённость обязательных зависимостей по актуальной предметной модели, а не по координатам/цвету карточек.
6. Рассчитать направление слева направо либо сверху вниз; подписать Human ID, короткое название, статус спеки и отдельное требование внимания. Длинные доказательства и варианты решения раскрывать по выбору.
7. Сохранить текущий вид. Новые события обновляют подписи/счётчики; автоматическая перераскладка и fit-view выполняются только при первом открытии или по команде пользователя.

Топологический порядок определяет допустимые слои, но не является календарным расписанием и не доказывает возможность параллельного запуска. Для critical path нужны длительности и дополнительные правила; произвольные «оценки» и проценты дрейфа не выводятся.

## 3. Словарь блок-схем

| Элемент | Обязательное содержание | Правило отображения |
|---|---|---|
| Действие | Глагол, исполнитель, область | Процессная карточка с подписью |
| Question | Вопрос, адресат, затронутая работа, blocking scope | Явный запрос человеку; confidence не закрывает его |
| Fork Ouro | Альтернативы с постоянными ID, последствия, рекомендация отдельно | Исключающий выбор, а не параллельный fork/join; выбранный путь подписан |
| Blocker | Наблюдаемое препятствие, evidence, допустимые планы | Одобрение плана и подтверждённое устранение показываются раздельно |
| Ожидание | Кого/чего ждём; какие ветви затронуты | Текстовое состояние, не только пульсация/цвет |
| Результат | Какая попытка и ревизия, чем подтверждён | `succeeded` агента отделён от приёмки DoD человеком |

Пути подписываются исходом: «выбран A», «проверка не пройдена», «нужны данные». «Да/нет» уместны, только если условие рядом однозначно сформулировано. Непринятые альтернативы обозначают возможное будущее; они не выдаются за свершившиеся события. Принципы человеческих задач и исключающего/параллельного выбора сверены с [OMG BPMN 2.0.2](https://www.omg.org/spec/BPMN/2.0.2/PDF); собственные карточки Ouro не объявляются BPMN-совместимыми.

Для пересечения ответственности применять три дорожки «Человек / Агент / Система», когда они помогают читать процесс. Внешний оркестратор остаётся отдельным контекстом; запрос остановки не рисуется подтверждённой остановкой до ACK. Переход после выбора должен иметь guard и явное событие применения, как предусмотрено таблицами состояний и принципами [W3C SCXML](https://www.w3.org/TR/scxml/).

## 4. Reality: воспроизводимое объяснение результата

- Узел — конкретное событие с `eventId`, `sequence`, `occurredAt`, `recordedAt`, автором, `specRevisionId` и при наличии `executionId`/`decisionRequestId`.
- Причинная ссылка указывает на существующее событие. Не выводить связь автоматически из близости во времени. Для внешнего предшественника допустимо явно хранить недоступный источник, не выдумывая его содержание.
- Повтор проверки и retry исполнения создают новые ID; ошибка в описании исправляется новым событием со ссылкой на прежнее.
- Журнал сортируется серверной последовательностью; отличающееся время внешнего агента не переставляет авторитетный порядок приёма фактов.
- Выбор исторического момента строит read-only проекцию. Старая ревизия и прежние решения остаются доступными. Replay восстанавливает данные и не повторяет команды внешним системам.

Эти правила применяют [Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html) и разделение записи/проекций из [CQRS](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs). Конкретные поля и ограничения проверяются контрактами Ouro.

## 5. Читаемость, доступность и стабильность

Один набор данных имеет граф, список и журнал. Выбранная спека сохраняет идентичность при смене вида; фильтр не скрывает наличие ожидающих решений без счётчика. Таблица даёт путь к зависимостям и формам без перетаскивания. Статус обозначается текстом и при необходимости иконкой, а цвет лишь дополняет смысл. Сохраняются видимый focus и логичный порядок Tab; aria-подпись узла содержит Human ID, название и состояние. Уменьшенное движение не убирает информацию.

Основания: [WCAG 2.2](https://www.w3.org/TR/WCAG22/) 1.4.1, 2.1.1, 2.4.7, 2.5.7; [React Flow Accessibility](https://reactflow.dev/learn/advanced-use/accessibility). Это целевые требования проверки, а не декларация соответствия всем WCAG.

Для простого DAG выбран [Dagre через React Flow](https://reactflow.dev/learn/layouting/layouting). Вложенные группы, внешние связи между ними и сложные порты требуют отдельного сравнения с [ELK Layered](https://eclipse.dev/elk/reference/algorithms/org-eclipse-elk-layered.html). Алгоритм раскладки не меняет предметные рёбра и не снимает запрет циклов.

## 6. Приёмочный набор диаграмм

| Набор | Что проверить |
|---|---|
| Цепь A → B → C | Одно направление чтения; C → A отклоняется с цепочкой цикла |
| Ромб A → B/C → D | Обе обязательные предпосылки D учитываются; сходящиеся линии читаемы |
| Два независимых компонента | Нет выдуманной связи; обе группы доступны в графе и таблице |
| Длинные русские названия | Карточки не обрезают смысл; детали доступны без zoom до микротекста |
| Два блокирующих решения | Ответ на одно не закрывает второе и не возобновляет исполнение автоматически |
| Повтор проверки после ошибки | Два отдельных факта со связью, а не один переписанный узел |
| События при выбранном узле | Выбор/камера/фокус стабильны; новые события видны счётчиком |
| Клавиатурный путь | Создание зависимости, выбор спеки и решение доступны без drag |

Проверки больших графов, screen reader и измерения качества раскладки добавляются при расширении объёма. Непроверенный масштаб не объявляется поддержанным.
